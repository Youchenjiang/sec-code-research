## Q1：ANOTA 是根據人工註解來判斷內容差距，然後再產出建議修改嗎？

**不是。ANOTA 不產出任何修改建議，它也不是比對「內容差距」。** 它是一個 sanitizer（偵測器）：比對的是「程式**執行時的實際行為**」與「人寫的政策」，唯一的產出是「哪個輸入違反了哪條政策」。

### 實際流程（Figure 1 的 ①–⑤）
1. **人寫註解**（①）：人宣告預期行為，例如「這段程式不得連到 youtube.com」。
2. **Fuzzer 產生大量輸入並執行程式**（②）。
3. **執行到註解時解析成政策**（③）。
4. **Monitor 監看執行**（④）：攔截 syscall、變數讀寫、資料流、程式區段執行，與政策比對。
5. **違規 → 回報**（⑤）：monitor 通知直譯器主動觸發 segfault，fuzzer 視為 crash 並保存觸發的輸入。

### 以論文的 motivating example 走一次（Listing 1 / 3）
- 原始程式用 `urlparse` 取 scheme / hostname，命中黑名單就 return，否則 `urlopen`。
- 人加的註解：`SYSCALL.NETWORK.BLOCK.SCHEME("file", ...)`、`SYSCALL.NETWORK.BLOCK.HOST("youtube.com", ...)`。
- Fuzzer 產生 `" https://youtube.com"`（開頭有空白）→ `urlparse` 解析錯誤，黑名單檢查被繞過 → `urlopen` 真的連到 youtube.com。
- eBPF 看到這個網路 syscall 違反 HOST 政策 → crash → Atheris 存下這個輸入。

> 註（Q11 核對）：論文只說加上 Listing 3 的註解即可偵測此漏洞（Section III-B2），上述「fuzzer 產生空白輸入 → 被抓到」是依設計重建的示意流程，論文沒有報告這次實際執行；`HOST` 政策在 syscall 層如何比對主機名稱，論文也未說明。

### ANOTA 給你什麼、不給你什麼
| 給 | 不給 |
| :--- | :--- |
| 觸發違規的輸入（crash input） | 為什麼程式允許了這個行為（根因） |
| 被違反的是哪一條政策 | 缺失檢查 vs. 檢查無效（Missing / Ineffective）的區分 |
| 違規發生的時間點（症狀點） | 應該在哪裡修、怎麼修 |

論文對報告格式只說違規會被「納入漏洞報告」，沒有更多描述。後續都是**人工**完成：所有發現皆人工驗證（Section V-B），再依各專案流程回報給開發者，由作者協助開發者修補（Section IX）。

### 與 Y2 的關係：症狀點 ≠ 缺陷點
上例中，ANOTA 報警的位置是 `urlopen` 發出網路 syscall 的那一刻（**症狀點**），但真正的缺陷在前面——`urlparse` 的解析錯誤導致黑名單檢查形同虛設（**缺陷點**，而且是 Ineffective Check，不是 Missing）。ANOTA 只告訴你「政策被違反了」，從症狀點回推到缺陷點、判斷失效型態、找出應修補的位置，正是 Y2 要做的事。

## Q2：為什麼論文的程式碼圖片（Listing）裡沒看到人類註解？

**因為 ANOTA 的「註解（annotation）」不是 `#` 或 `//` 那種程式碼註解（comment），也不是 Java 的 `@Annotation`，而是寫在程式裡的普通函式呼叫。** 論文在 Listing 中以**綠色底色**標示這些行。

### 為什麼設計成函式呼叫
Section IV-A：為了不改動 Python 語法，註解在語法上就是一般的函式呼叫。修改後的 CPython 在 `CALL_FUNCTION` opcode 掛 hook，每次呼叫函式時檢查名稱是否為註解（`SYSCALL`、`TAINT`、`WATCH`、`EXECUTION`、`CLEAR`），是的話就把參數解析成執行期政策。也因此註解是「執行到才生效」，可以在程式中途開啟或用 `CLEAR` 關閉。

### 各 Listing 中的註解位置
| Listing | 語言 | 註解行（綠底） | 作用 |
| :--- | :--- | :--- | :--- |
| 1 | Python | **無** | 原始有漏洞的程式（motivating example），本來就沒加註解 |
| 2 | PHP | 第 2 行 `TAINT($user_credential, sanitization=[hash]);` | 憑證未經 hash 不得寫入檔案 |
| 3 | Python | 第 2–3 行 `SYSCALL.NETWORK.BLOCK.SCHEME(...)`、`SYSCALL.NETWORK.BLOCK.HOST(...)`；第 6 行 `SYSCALL.NETWORK.CLEAR()`（未上綠底，但也是註解） | Listing 1 加上註解後的版本 |
| 4 | JavaScript | 第 4 行 `SYSCALL.FILE.ALLOW(staticDir);` | 檔案存取只限 static 目錄 |
| 5 | Python | 第 2 行 `EXECUTION.BLOCK()`、第 4 行 `WATCH.ALLOW(user_list, "r")` | 只有管理員可增刪使用者 |

> Listing 2（PHP）與 Listing 4（JavaScript）只是示意，原型實作僅支援 Python。

### 讀 Listing 時容易困惑的兩處（論文未說明）
1. **Listing 3 把原本的過濾程式碼拿掉了**：Listing 1 第 2–9 行（黑名單與 `urlparse` 檢查）在 Listing 3 中消失，看起來像是「註解取代了檢查」。依論文本意，註解是加在原程式上的政策，原檢查應仍存在（否則 CVE-2023-24329 的繞過情境就不成立），推測是為了版面而省略。
2. **Listing 5 的 `EXECUTION.BLOCK()` 沒有條件參數**：Table II 的範例是帶條件的 `EXECUTION.BLOCK(user.type != 'admin')`，但 Listing 5 寫在 `if is_auth:` 底下且不帶參數，論文沒解釋無參數時的語意；照字面讀甚至像是「已認證者不得執行」，與「只有管理員可新增使用者」的說明相反。引用此例時需注意。

### 對 Y2 的意義
ANOTA 的政策是**插入在原始碼中的可執行呼叫**，本質上與 Y2 的「斷言探針（assertion probe）」是同一種東西：都是在特定位置插入一行執行期檢查。差別在於 ANOTA 由人決定寫什麼、放哪裡；Y2 要從 exploit trace 自動決定。

## Q3：所以每個註解就相當於一個單元測試？

**不太一樣。註解比較像「單元測試的後半段」——只有判斷對錯的規則（oracle），沒有輸入。** 更貼切的類比是 `assert`／不變量（invariant），或 ASan 這類 sanitizer。

### 單元測試 vs. ANOTA 註解
| | 單元測試 | ANOTA 註解 |
| :--- | :--- | :--- |
| 組成 | **特定輸入** ＋ 預期結果 | 只有**規則**（什麼行為不允許），沒有輸入 |
| 輸入從哪來 | 測試者自己寫死 | Fuzzer 大量產生 |
| 檢查範圍 | 這一個情境 | 所有跑到這裡的輸入，在 `CLEAR` 前持續有效 |
| 檢查什麼 | 通常是回傳值或最終狀態 | **執行過程中**的行為：syscall、資料流、變數讀寫、程式區段，包含第三方函式庫與 C 擴充模組內部 |

組合起來看：**Fuzzer 提供輸入 ＋ 註解提供 oracle ≈ 一個完整的測試**，概念上接近 property-based testing（例如 Python 的 Hypothesis：寫「性質」，由工具產生輸入）。

### 用 motivating example 對比
- **單元測試**：`SafeURLOpener` 無論是否擋下都回傳 `None`（擋下時 `return`，沒擋下時只 `print`），所以 `assert SafeURLOpener(...) is None` 永遠通過，測不到任何東西。正確寫法是 mock 掉 `urlopen`，確認它沒被呼叫：
  ```python
  with mock.patch("urllib.request.urlopen") as m:
      SafeURLOpener(" https://youtube.com")   # 開頭有空白
      m.assert_not_called()
  ```
  只要放進這個帶空白的輸入，單元測試**一樣能抓到這個漏洞**。
- **ANOTA 註解**：`SYSCALL.NETWORK.BLOCK.HOST("youtube.com")` → 只要程式**實際**連到 youtube.com 就報警。

**就這個案例而言，註解相對單元測試沒有優勢**；找到那個帶空白的輸入靠的是 fuzzer，不是註解。單元測試搭配 fuzzer 或 property-based testing 也有機會找到。

### 真正的差異：判斷對錯的依據從哪裡來
- **單元測試**的預期結果，來自開發者對「哪些輸入算是 youtube」的理解。如果測試裡也用 `urlparse` 判斷 host，測試與程式會被同一個 parser 錯誤騙過，一起通過。
- **ANOTA** 的判斷依據是程式**實際連到了哪裡**（syscall 層級觀察到的事實），與被測程式的邏輯無關。

另一個實務差異：此漏洞是**副作用**（真的發出連線），只檢查回傳值的單元測試看不到，必須事先想到要 mock 哪個函式；ANOTA 直接在 syscall 層監控，不需要事先知道副作用會從哪個函式發出。

### 補充：這個 motivating example 本身說服力有限
它本質上是 **SSRF 過濾被繞過**（parser 解析不一致導致的輸入驗證問題），屬於注入／輸入驗證類，並非典型業務邏輯漏洞（**此為本紀錄的分類；論文把它當業務邏輯漏洞的例子**），修法也直接（輸入正規化、改用白名單）。這與 ANOTA 成果集中在 syscall 類漏洞、授權與流程類最弱的分布一致。Y2 在 proposal 中引用 ANOTA 時，不宜拿此例代表業務邏輯漏洞；Ineffective Check 的案例也應改用授權或流程類的真實 CVE。

### 兩者其實會一起用
論文 Section V 中，ANOTA 把專案**既有的單元測試改寫成 fuzzing harness**：單元測試提供「怎麼呼叫程式」的入口與輸入結構，fuzzer 從這裡開始變異，註解負責判斷是否違規。

### 對 Y2 的啟示
Y2 的斷言探針也是 assert／不變量，不是單元測試。但 RQ2 目前的驗證方式（重播 PoC 必須被擋、重播正常流程必須通過）本質上是**固定輸入的單元測試**，因此測不出探針是否只是「剛好擋住這一個 PoC」。這一點之後討論 RQ2 時可能需要處理。

## Q4：Q3 說了那麼多都代表 ANOTA 沒用，結論是 ANOTA 根本是廢物？

**不是。** Q3 的結論只適用於 motivating example 這個**單一案例**（SSRF 過濾被繞過，單元測試放對輸入就能抓到）。修訂 Q3 時重點都放在這個例子的弱點，沒有寫出 ANOTA 真正有價值的地方，才讀起來像「ANOTA 沒用」。

### 單元測試做不到、ANOTA 做得到的三件事

**1. 追蹤資料「流到哪裡」，而不只檢查單一輸出（Data Flow）**
以 Listing 2 為例：憑證不得未經 hash 寫進 log。單元測試要做到同等效果，必須呼叫**所有**會寫 log 的路徑、攔截**所有**輸出管道（檔案、例外訊息、第三方函式庫內部的 logging），再檢查憑證有沒有以任何形式出現。`TAINT` 則是標記資料本身：不管經過幾層函式、被格式化進哪個字串，只要帶著 taint 抵達 sink 就報警（純 Python 套件自動涵蓋；C 擴充模組需用 ANOTA 的 LLVM pass 重新編譯才追得到）。Table IV 的 22 個 0-day 中有 12 個是 Data Flow 類（log 洩漏 6、TOCTOU 4、計時側信道 2），包含定期做安全稽核的 Home Assistant Core 與有 bug bounty 的 Apache Airflow（這些專案都有測試套件——論文正是拿它們改寫成 harness——但既有測試沒有發現這些問題；此為推論）。

**2. 一條政策覆蓋所有路徑**
例如 `SYSCALL.FILE.ALLOW(staticDir)` 一行，就約束了之後**所有**檔案相關 syscall，包含第三方函式庫與 C 擴充模組內部發出的呼叫。單元測試是一條路徑、一個情境地寫。

**3. 觀察 syscall 層級的行為順序**
TOCTOU 是「先檢查、後使用」兩個 syscall 之間的時間差，單元測試很難觀察；ANOTA 的 eBPF 監控能直接看到這個順序。論文為減少雜訊，只對**含敏感資料（經 Data Flow 標記）的檔案**回報 TOCTOU。

### 實證面
- 22 個 0-day、17 個 CVE，包含 4 個有 bug bounty 的專案；每個專案約花 1 小時寫註解。
- 消融實驗中，原生 fuzzer 即使**直接拿到觸發漏洞的輸入**也偵測不到（因為程式不會 crash），證明「缺 oracle」是真問題，ANOTA 補上了。

### 平衡評價
| 強項 | 弱項 |
| :--- | :--- |
| 資料流類（敏感資訊洩漏、log 洩漏） | 授權與流程類（依實驗結果分布判斷；作者在 V-D1 只就單一存取控制題承認「非理想標的」，未承認整個類別是弱項，見 Q11） |
| syscall 類（path traversal、SSRF、上傳、code injection、TOCTOU） | Motivating example 選得不好，用注入類案例推銷「業務邏輯 sanitizer」 |
| 判斷依據獨立於被測程式邏輯 | 評估有偏差（標註者知道 CWE 類型、ablation 對照組必然為 0；此為本紀錄的批評，論文把「只告知 CWE 類型」當作降低偏差的措施） |
| 一條政策覆蓋所有路徑與第三方程式碼 | 僅支援 Python |

### 對 Y2 的意義
把 ANOTA 說成「沒用」對 Y2 反而不利——打敗一個沒用的對手沒有學術價值。比較有利的定位是：**ANOTA 在 syscall／資料流類有效，但在授權與流程類卡在「政策難寫」**；Y2 正好針對這個弱項，從 exploit trace 推出授權與流程類的 invariant。ANOTA 是 Y2 的互補，而非被否定的對象。

## Q5：意思是 ANOTA 跟我們上次的計畫（SecVerify）比較像？

**是，就「解決的問題」與「擅長的漏洞類型」而言，ANOTA 與 SecVerify 的相似度高於現在的 Y2。** 但兩者也不完全相同。
（參照：[archive-secverify/README.md](../../../archive-secverify/README.md)、[SecVerify 研究流派對照指南.md](../../../archive-secverify/SecVerify%20研究流派對照指南.md)、[SecVerify 第二年重新設計三大動態驗證方案評估.md](../../../archive-secverify/SecVerify%20第二年重新設計三大動態驗證方案評估.md)）

### 相似之處
| 面向 | SecVerify | ANOTA |
| :--- | :--- | :--- |
| 核心問題 | 安全 oracle：怎麼判斷安全性被違反（流派 2B.5） | 同一個問題：fuzzer 缺業務邏輯 oracle |
| 技術手段 | 執行期插樁、攔截 sink（如 `Log.d`）、動態污點（2C.1、2B.2） | 執行期監控、`TAINT` 追蹤到 sink、syscall 監控 |
| Oracle 形式 | 把安全不變量轉成 `assertTrue/False` | 把安全政策寫成註解，違反即 crash |
| 擅長類型 | 資料外洩（log、SharedPreferences）、元件權限等技術型漏洞 | 資料流（log 洩漏）、syscall 類（path traversal、SSRF） |

### 不同之處
| 面向 | SecVerify | ANOTA |
| :--- | :--- | :--- |
| 起點 | SAST 報告（已有疑似漏洞點） | 沒有起點，人寫政策後由 fuzzer 探索 |
| 目標 | 驗證／過濾靜態分析誤報 | 發現未知漏洞 |
| Oracle 來源 | **自動生成**（LLM／安全規範） | **人工撰寫** |
| 輸入 | 生成的固定 payload（單元測試形式） | Fuzzer 大量產生 |
| 平台 | Android（Kotlin/Java） | Python |

### 兩個值得注意的交集
1. **SecVerify 面向二（自動生成安全斷言）正是 ANOTA VI.C 的未來工作**：ANOTA 把「自動產生政策」留給未來，而 SecVerify 當初要做的就是自動產生 oracle。若要說誰在延續 ANOTA 的 future work，SecVerify 比 Y2 更直接。
2. **SecVerify 重新設計時遇到的「Mock 循環論證」，ANOTA 用 syscall 層監控解掉了**：SecVerify 1.0 被質疑大量 mock `Log.d` 等 sink 只是在測 mock 本身；ANOTA 用 eBPF 觀察真實 syscall、用修改過的直譯器追蹤真實資料流，不靠 mock。這也是 Q3 中 mock `urlopen` 寫法的同一個弱點。

### 與現在 Y2 的距離
| | ANOTA | Y2 |
| :--- | :--- | :--- |
| 漏洞是否已知 | 否（要去發現） | 是（Y1 已打穿） |
| 產出 | 違規輸入 | 根因、失效型態、風險矩陣 |
| 擅長類型 | syscall／資料流 | 授權／流程（ANOTA 最弱處） |

### 對現在計畫的意涵
ANOTA 目前被放在 Y2 資料夾、當作 Y2 的「對標」，但從定位看：
- 它解的 oracle 問題更接近 **Y1**（判斷黑箱攻擊是否成功）與 **Y3**（修補後的回歸 oracle），`ANOTA_論文價值與參考借鑑.md` 已有對 Y1、Y3 的借鑑段落；
- 對 Y2 主要是**動機**（授權類政策難寫，V-D1／VI.C）與**互補**，不適合當正面比較的 baseline。

## Q6：所以 ANOTA 是作者自己造了一套語法規則，還要工程師學會後去標註自己的程式碼才能用？

**基本上是。** 作者自訂了一套小型語法（System Call、Data Flow、Object Access、Code Execution、Clear 五類），以函式呼叫的形式寫進原始碼，必須有人學會後動手標註。但有幾點補充：

### 1. 「誰來標」不一定是原開發者
論文說使用者可以是開發者或安全分析師。實際評估中**全都是外人標註別人的程式碼**：
- 已知漏洞重現：由熟悉 ANOTA 的作者標註，共花 10 個工作天；
- 0-day 挖掘：作者標註，每個專案約 1 小時；
- 使用者研究：11 位學生標註陌生應用，經簡短訓練後成功率 83.3%。

### 2. 學習成本：作者說不高，但業界受訪者認為是最大障礙
- 語法只有五類，學生研究中「所有參與者都認為語法容易上手」；10/11 人覺得寫黑名單（blocklist）比白名單（allowlist）有把握。
- 但 10 位業界開發者訪談中，**10/10 把「學一套新註解語言」列為最主要的導入障礙**，6/10 擔心整合 CI/CD 的成本，2 位擔心註解沒有統一風格會降低可讀性（Section V-D2）。

### 3. 不只要學語法，還要換執行環境（容易被忽略）
要讓註解生效，需要：
- **修改過的 CPython 直譯器**（標準 Python 無法執行這些註解）；
- **eBPF 監控程式**（論文以 Aya／Rust 實作；「Linux 限定、載入通常需要特權」是 eBPF 的一般限制，論文未討論）；
- C/C++ 擴充模組要用 ANOTA 提供的 **LLVM pass 重新編譯**；
- 一個 **fuzzing harness**（論文把專案既有單元測試改寫而成）。

另外，註解是寫在原始碼裡的函式呼叫，**正式上線時這些呼叫如何處理（是否需要空實作的 stub 或建置時移除），論文沒有討論**。

### 4. 自訂標註語言本身不稀奇
這是常見做法：契約式設計（JML）、Meta Pysa 的 source/sink 設定檔、同一團隊（Holz、Abbasi）先前的 IJON 也是讓人在程式碼中加註解引導 fuzzer。論文 Appendix A 也指出 Pysa、ZAP 一樣需要大量人工設定。ANOTA 的核心主張是「政策與機制分離的框架」；不過論文也把「設計一套輕量註解系統」列為貢獻之一（Section I Contributions），說「不在語法本身」是本紀錄的看法。

### 對 Y2 的意義
「要人學語法、要人知道政策、要人動手標」這三重成本，正是 Y2 從 exploit trace 自動推導 invariant 的動機。Y2 的探針由系統產生，開發者不需要學任何語法；但 Y2 的探針同樣需要某種執行期環境才能驗證，這部分的部署成本在設計時也要考慮。

## Q7：所謂的註解到底是用來引導 fuzzer，還是做為 oracle 判斷？

**只做 oracle，不引導 fuzzer。**

### 分工
| 元件 | 負責 | 是否受註解影響 |
| :--- | :--- | :--- |
| Fuzzer（Atheris；Web 應用另加 custom mutator） | 產生、變異輸入；以**程式碼覆蓋率**決定往哪裡探索 | **否**——論文只描述違規以 crash 回報，沒有任何把註解資訊回饋給變異策略的機制（此為依設計推論，論文未明文否定） |
| 註解＋Policy Monitor | 判斷這次執行是否違反政策；違反就讓程式 crash | — |

Fuzzer 從頭到尾不知道註解寫了什麼，它只會看到「這個輸入讓程式 crash 了」，然後把該輸入存下來。註解是**終點判定**，不是**方向指引**。

### 論文自己畫出的界線：與 IJON 的對比
論文 Related Work（Section VII）明確區分：IJON（同團隊先前的作品）用註解**引導** fuzzer 探索更深的程式狀態，但判斷是否有 bug 仍靠傳統的 crash；ANOTA 則相反，註解用來**定義新的漏洞類型**（oracle），探索仍交給一般 fuzzer。
> Q6 提到 IJON 時把它和 ANOTA 並列為「自訂註解」的例子，但兩者用途不同：IJON＝引導，ANOTA＝判定。

### 容易混淆的地方：論文中確實有「引導」，但不是註解做的
為了讓 fuzzer 更容易觸發漏洞，作者另外做了兩件事，**都與註解無關**：
- Web 應用的 **custom mutator**：集中變異 cookie、query 參數、header、URL；
- **惡意 payload 字典**：內建反序列化與 code injection payload，設計成容易被 policy monitor 抓到。

### 帶來的限制
因為註解不引導探索，**能不能觸發違規完全取決於 fuzzer 自己能不能走到那個狀態**。論文中的例子：ZenML（Table III ID 46）的漏洞需要「A 建立邀請連結 → B 註冊 → B 修改 A 的密碼」這種多步驟前置條件，fuzzer 走不到，註解寫對了也抓不到；作者手動提供含邀請連結的種子後，驗證 ANOTA+FUZZER「理論上」可以偵測（論文用語）。這種多步驟、跨使用者的情境，正是授權與流程類漏洞的常態。

### 對筆記的修正
`ANOTA_論文核心技術解讀.md` 的流程圖原本寫「Crash → 引導變異 → Fuzzer」，與論文不符，已改為「回報 crash，保存觸發輸入（不影響變異方向）」。

## Q8：為何作者堅持在執行期（Runtime）分析，而不是直接讓 Agent 自主進行滲透測試？

**先說明：論文完全沒有討論 Agent 滲透測試**，LLM 只在 VI.C 以「輔助產生註解」的角色出現。以下分為「論文有寫的依據」與「我的推論」兩部分。

### 一、論文有寫的依據

**1. 黑箱看不到內部狀態（Appendix A）**
與 ZAP、Wapiti 這兩個黑箱動態掃描器比較時，作者把它們表現差歸因於黑箱限制與覆蓋率淺，例如 ZAP 無法區分讀取與寫入權限，因此漏掉多個漏洞。ANOTA 的論點是：判斷要放在**程式內部**，才看得到黑箱看不到的東西。

**2. 業界現況就是靠人工滲透測試，而且很吃力（Section V-D2）**
受訪的 10 位開發者中，10/10 靠人工 code review、9/10 靠外部滲透測試偵測業務邏輯漏洞。作者用這點說明問題仍是「耗費人力的挑戰」，ANOTA 定位為降低這份人力。

### 二、我的推論（論文未明說）

**1. ANOTA 抓到的漏洞，大多從外部根本看不到**
22 個 0-day 中：
- CWE-532 log 洩漏 6 個：憑證被寫進**伺服器本機的 log 檔**，HTTP 回應完全正常；
- CWE-367 TOCTOU 4 個：兩個 syscall 之間的時間差，外部無從觀察；
- CWE-208 計時側信道 2 個：需要統計量測執行時間。

外部的 Agent 再聰明，也看不到伺服器把密碼寫進了哪個檔案。這類漏洞**只能從內部觀察**，這可能是作者選擇 runtime 的根本原因。

**2. Agent 一樣有 oracle 問題，而且更難**
Agent 打完一輪後，仍要判斷「這算攻擊成功嗎？」對業務邏輯漏洞而言，回應常常是正常的 200 OK。Agent 只能從 UI、文件**猜測**預期政策——這正是論文批評的「用啟發式推測上下文」，還多了 LLM 幻覺風險（作者在 VI.C 就是以幻覺為由，要求 LLM 產生的註解須經人工驗證）。

**3. 可重現性與成本**
Fuzzing＋crash oracle 便宜、可重複、可跑數百萬次；Agent 滲透測試成本高、結果不確定，在學術評估上較難做出可比較的實驗。另外，論文的 0-day 都在 2024 年取得 CVE，研究主要在 2023–2024 年進行，當時 LLM 滲透 Agent 還不成熟。

### 三、關鍵：「Runtime」與「Agent」其實不是二選一
ANOTA 是 **oracle**，fuzzer 是**輸入產生器**，兩者可替換。把 Atheris 換成滲透 Agent，ANOTA 一樣可以當 Agent 的 oracle。真正的取捨是：

| | 外部 oracle（Agent 看回應判斷） | 內部 oracle（ANOTA 看執行期行為） |
| :--- | :--- | :--- |
| 需要原始碼／改環境 | 不需要 | 需要（改過的直譯器、eBPF） |
| 看得到副作用（log、檔案、syscall） | 看不到 | 看得到 |
| 預期政策從哪來 | Agent 推測 | 人寫明 |

### 對本計畫的啟示
這剛好解釋了 Y1 與 ANOTA 的適用範圍為何不同：
- **授權類（BOLA）通常從外部看得到**：用兩個帳號交叉存取，若 A 拿到了 B 的資料，回應本身就是證據 → 適合 Y1 的黑箱 Agent。
- **ANOTA 擅長的類型（log 洩漏、TOCTOU）從外部看不到** → 必須在內部觀察。

因此 Y1 選擇 Agent 滲透、ANOTA 選擇 runtime，各自對應的是不同可觀察性的漏洞類型，不是誰對誰錯。

## Q9：三個追問
1. 測內部洩漏，模擬內部連線不就能測了？
2. 駭客難道測不出 IDOR／BOLA 嗎？
3. 選 Fuzz 而非專業滲透工具來測安全性，不就是把汽車加裝軌道拿來當火車用？

### 9-1：可以，而且這修正了 Q8 的說法
Q8 說 log 洩漏「只能從內部觀察」是對的，但**內部觀察不等於需要 ANOTA**。給測試者灰箱權限（讀伺服器 log、檔案系統、監看對外連線）就能測。實務上常見做法是 **canary（誘餌）值**：植入一個獨一無二的假憑證，跑完測試後搜尋系統寫出的所有檔案與網路流量，找到就代表洩漏。這個方法簡單有效，ANOTA 在 log 洩漏上的優勢比 Q8 暗示的小。

ANOTA 的 taint 相對 canary 剩下的優勢：
- 資料被**轉換**後仍追得到（例如 base64 編碼、截斷、拼接進其他結構），canary 字串搜尋會漏；
- 不必事先知道**該去哪裡找**（暫存檔、例外訊息、第三方套件的 log；論文 Munki 案例中 token 被寫進 `mkstemp()` 產生的 curl 設定檔——注意該案例經開發者確認是**預期行為、屬誤報**，這裡只拿來說明落點可能出乎意料）。

TOCTOU 與計時側信道仍需 syscall 或時間量測層級的觀察，簡單的灰箱檢查做不到。

### 9-2：測得出來，這與 Q8 的結論一致
BOLA 是 OWASP API Top 10 第一名，滲透測試與 bug bounty 最常回報的類型之一，有現成工具（如 Burp 的 Autorize 擴充套件，用兩個帳號交叉重放請求）。Q8 的結論正是「BOLA 從外部看得到，適合 Y1 的黑箱 Agent」，不需要 ANOTA。

外部測試的實務門檻（不是做不到，而是要多花工夫）：
- 需要**多個帳號**，並知道哪個物件屬於誰；
- 物件 ID 需可取得（UUID 無法列舉時要另找洩漏點）；
- **寫入型 BOLA**（改／刪別人的資源）回應可能只是 200 OK、不帶資料，需用另一個帳號回頭確認狀態是否被改。

外部測試給不了的，是「程式哪裡少了檢查、還有哪些進入點共用同一個缺陷」——這正是 Y2 的範圍。

### 9-3：對 Web 業務邏輯來說，這個比喻大致成立；對函式庫類漏洞則不成立

**支持比喻的證據（論文本身）**：
- 覆蓋率導向 fuzzing 原本是為解析器、原生程式找 crash 設計的。ANOTA 用在 Web 上時，必須額外加裝「軌道」：自訂 mutator（變異 cookie、header、URL）、payload 字典、把單元測試改寫成 harness、保留登入 session。
- 多步驟、多使用者的情境 fuzzer 走不到（ZenML 案例需人工提供種子）。
- 授權與流程類正是 ANOTA 最弱的類型。

**不支持比喻的部分**：
- **論文其實有與專業工具比較**：Appendix A 比了 ZAP、Wapiti（DAST 掃描器）與 Semgrep、SonarQube、Pysa，ANOTA＋fuzzer 在 35 個靶場漏洞上全數偵測，ZAP 17 個。但此比較有偏差（標註者知道漏洞存在、靶場是刻意留洞的應用、沒有比 Burp 或人工滲透）。
- **很多標的根本不是 Web 服務**：Table III/IV 有大量函式庫（langchain、onnx、Transformers、Paddle、fonttools、untangle 等），沒有可以「滲透」的服務端點，滲透工具無從下手；fuzzing harness 可以直接呼叫函式庫 API。
- **目標不同**：滲透測試是定期、外部、昂貴的專家服務；fuzzing＋sanitizer 的目標是像 ASan 透過大規模 fuzzing（論文引用 ClusterFuzz）那樣自動化地跑（論文 Section I 的願景；「每次 commit 跑」是本紀錄的延伸，CI/CD 整合在論文中是導入障礙與未來工作）。兩者是互補，不是替代。

### 小結
| 漏洞類型 | 較適合的方法 |
| :--- | :--- |
| Web 授權／流程類（BOLA、IDOR、跳步） | 滲透測試／Agent（外部可觀察，需要多步驟與多帳號） |
| 函式庫的 syscall 類（path traversal、XXE、反序列化） | Fuzzing＋sanitizer（沒有服務端點可滲透） |
| 敏感資料洩漏 | 灰箱 canary 檢查即可大致處理；資料會被轉換或落點未知時，taint 較完整 |
| TOCTOU、計時側信道 | 需要執行期內部觀察 |

> 註：上表「函式庫」一列容易被讀成「ANOTA 只適用於函式庫」，此說法過窄，見 Q10 更正。

## Q10：照這樣講，代表這篇的價值只適用於函式庫？

**不是，這是對 Q9 小結的更正。** Q9 提到函式庫，只是舉「滲透工具碰不到」的例子，並不代表 ANOTA 只能用在函式庫。

### 證據：Table IV 的 22 個 0-day 超過一半在 Web 應用或服務上（專案類型為本紀錄自行歸類，論文未分類）
- **檔案上傳（CWE-434）**：Apache Superset、calibre-web、cmdb、OpenAgents，都是 Web 應用（論文未說明各漏洞使用哪種 harness）；
- **log 洩漏（CWE-532）**：Home Assistant Core、FileCodeBox、SolidUI、nebari；
- **TOCTOU（CWE-367）**：Apache Airflow、ArchiveBox、ZenML。

Table III 也有大量 Web 應用：label-studio、gradio、mlflow、MobSF、wagtail、indico、changedetection.io 等。

### 較準確的切法：不是「函式庫 vs. Web」，而是以下兩個維度（本紀錄的歸納，非論文主張，見 Q11）
| 維度 | ANOTA 有優勢 | ANOTA 弱 |
| :--- | :--- | :--- |
| 漏洞後果發生在哪 | **系統內部的副作用**：檔案寫錯位置、憑證進 log、危險 syscall、TOCTOU | 後果直接反映在回應裡（例如拿到別人的資料） |
| 觸發需要什麼 | **單一請求或少數步驟**即可觸發 | 多步驟、多帳號、需特定狀態（如 ZenML 邀請流程） |

Web 應用中屬於左欄的漏洞很多，ANOTA 在這些地方都有價值；右欄才是滲透測試／Agent 的主場。

### 即使與滲透測試能力重疊，ANOTA 仍有的價值
Q9 同意上傳類等漏洞滲透測試者從外部也可能找到，但 ANOTA 仍有：
1. **自動化、可持續**：可在每次 commit 執行，不必每次請專家；
2. **不需滲透專業**：開發者寫幾行政策即可，學生研究成功率 83.3%；
3. **框架本身**：「政策與機制分離」——只要能把預期行為寫成政策，執行期就能檢查。這一點與漏洞落在哪裡無關，也是對 Y2 最有參考價值的部分。

## Q11：Q1–Q10 的看法跟論文作者的看法一樣嗎？

**不一樣的地方不少。** 以下列出 Q1–Q10 中，本紀錄的看法與作者在論文中的看法所有不同之處。

| 議題 | 作者的看法 | 本紀錄的看法 | 相關題 |
| :--- | :--- | :--- | :--- |
| **適用範圍** | ANOTA 是「業務邏輯漏洞」的通用 sanitizer；四類註解依 CWE Top 40 中業務邏輯漏洞的執行期行為設計，足以涵蓋這些 CWE；授權與認證類是動機中的頭號例子（I、II-A、III-A） | 從實驗結果分布看，實際強在 syscall 類（path traversal、上傳、code injection）與資料流類（log 洩漏、TOCTOU）；授權與流程類最弱（22 個 0-day 中 Object Access 1 個、Code Execution 0 個） | Q4、Q5、Q10 |
| **Motivating example 的性質** | `urlparse` 空白繞過是需要理解業務邏輯才能偵測的漏洞；靜態分析與動態分析都會失敗，只有比對執行期行為與應用特定的政策才能偵測（II-B） | 本質是 SSRF 過濾被繞過，屬注入／輸入驗證類，不是典型業務邏輯漏洞；單元測試只要放進那個帶空白的輸入，一樣抓得到，因此不足以支撐「只有 ANOTA 能偵測」 | Q3、Q9 |
| **授權類偵測失敗的原因** | 個別因素：changedetection.io 那題「不是理想標的」（開發者知道就會直接修）；Superset 是標註者理解不足；ZenML 是輸入種子不足；作者認為原開發者因熟悉業務邏輯，成功率會更高（V-A、V-D1） | 類別層級的限制：授權政策要寫得對，等於幾乎已經知道漏洞在哪（標註悖論）；加上授權與流程類常需多步驟、多帳號狀態，fuzzer 不易走到 | Q4、Q7 |

Y2 選哪一條、根據什麼選，才是 Y2 的核心研究問題。RQ2 目前的固定輸入重播（擋 PoC、放行正常流程）測不出這個差別，三條都能通過。

### 具體化的問法
> **Y2 從 exploit trace 推出的 invariant，正確性由什麼保證？如果保證不了，Y2 是否也只是把人的判斷換了一個位置？**

## Q13：Object Access 和 Code Execution 差在哪裡？

（依原文 `2026-f938-paper.pdf` §III-A、§III-B.3、§IV-B.2 核對）

**一句話**：Object Access 管的是「**這份資料**誰能碰」，Code Execution 管的是「**這段程式**誰能走到」。

| | Object Access | Code Execution |
|---|---|---|
| 語法 | `WATCH.[ALLOW\|BLOCK](物件, 權限)`；另有 `WATCH.CON(物件)` | `EXECUTION.BLOCK(條件)` |
| 綁在哪裡 | 一個**變數／物件** | 程式中的**一個位置** |
| 規則內容 | 對該物件的讀（r）、寫（w，含刪除）、執行（x，限可呼叫物件）是否允許；`WATCH.CON` 要求執行時間為常數（偵測時序旁路） | 程式執行到此處、且條件為真 → 違規；論文稱其「類似反轉的 assertion」 |
| 何時檢查 | 每次讀寫該變數時：把變數加入監看清單，攔截 Python 的 load/store opcode；C 擴充模組改用 ptrace 設讀寫中斷點 | 只在程式**走到註解那一行**時檢查一次 |
| 範圍 | 全域變數全域檢查；區域變數只在定義它的 stack frame 內檢查 | 只有註解所在那一點 |
| 論文範例 | Table II ⑤ `WATCH.ALLOW(admin_data,'r')`、⑥ `WATCH.BLOCK(admin_api,'x')` | Table II ⑧ `EXECUTION.BLOCK(user.type != 'admin')` |

**比喻**（我的說法）：Object Access 是鎖在**保險箱**上，不管從哪條路來拿都會被檢查；Code Execution 是守在**某一道門**口，只檢查走這道門的人。

**兩者常一起用**：§IV-B.2 說 improper access control 可用這兩種註解偵測；開發者知道哪段程式只有特權使用者能執行時用 Code Execution。Listing 5 同時用了兩者：`EXECUTION.BLOCK()` 標記新增使用者的程式段，`WATCH.ALLOW(user_list, "r")` 限制 `user_list` 只能讀。

**對 Y2 的意義**（推論）：
- Y2 的斷言探針「在某位置插一行檢查」，形式上接近 **Code Execution**（反轉的 assertion），因此也繼承它的限制：只檢查放置的那一點，同一筆資料有多個入口時要各放一個 —— 這正是 Y2 流程 ③ 要找出所有入口的原因。
- 兩者都不直接表達 BOLA 的「這**一筆**訂單的擁有者是不是目前使用者」：Object Access 監看的是程式變數，不是資料庫裡的某一列；論文的 Code Execution 範例是角色層級（`user.type != 'admin'`）。要表達擁有權，需把條件寫成 `order.owner != current_user`；我核對的 Table II 與 Listing 範例中沒有這種用法（未逐頁確認全文）。

## Q14：ANOTA 為何要分 Object Access 和 Code Execution 兩種？

### 論文給的理由（已核對原文）
1. **註解類型是依「攻擊時的異常行為」設計的**（§III-A）：作者分析 CWE Top 40 中的業務邏輯漏洞（Table I），歸納出四種異常行為 ——（1）非預期的系統呼叫、（2）**非預期的程式執行**、（3）**非預期的變數存取**、（4）非預期的資料流 —— 一種行為對應一種註解。Code Execution 對應（2），Object Access 對應（3）。
2. **存取控制漏洞有不同的被利用方式**（§III-B.3）：可能是「執行了特權程式邏輯」、「讀寫了特權變數」，或「碰到特權系統資源（檔案、網路）」。前兩者分別由 Code Execution 與 Object Access 處理，第三者由 System Call 處理。
3. **看開發者知道什麼**（§IV-B.2）：開發者知道「哪段程式只該給特權使用者執行」時，用 Code Execution。

論文**沒有討論**為何不合併成一種。

### 為何不合併（我的推論）
兩者各自補對方的盲點：

| 情況 | 適合 | 原因 |
|---|---|---|
| 同一份資料有多條路徑能碰到（例如管理頁和一支被遺忘的 API 都能改 `user_list`） | Object Access | 守在資料上，不論從哪條路來都會被檢查；Code Execution 只守放置的那一點 |
| 敏感的是「動作」而不是某個變數（例如寄信、退款、觸發外部服務） | Code Execution | 沒有單一變數可監看 |
| 規則依情境而定（例如「不是管理員就不准」） | Code Execution | 語法帶條件參數；`WATCH` 的語法只有物件與權限（r/w/x），沒有條件參數，情境只能靠註解放的位置表達（如 Listing 5 放在 `if is_auth` 內） |
| 成本 | Code Execution 較低 | 只在走到那一行時檢查一次；Object Access 要攔截每一次讀寫，且區域變數只在定義它的 frame 內有效 |

### 對 Y2 的意義（推論）
這個區分對應到 Y2 的「探針放在哪」：放在**程式位置**（像 Code Execution）便宜但只守一點，所以需要流程 ③ 找出所有入口；放在**資料存取點**（如 SQL 層，像 IDORacle 的做法）則不論從哪個入口來都會被攔，但要先知道哪些資料受保護。

## Q15：「可以解決 CWE Top 40 中發現的業務邏輯漏洞」是什麼意思？

（依原文 §III-A 與 Table I 核對）

原文的意思是：ANOTA 的註解語法「expressive enough to address」CWE Top 40 中的業務邏輯漏洞。這裡的 address 譯成「解決」容易誤解。

**實際意思**：註解語法的**表達能力夠用** —— 對這些漏洞類型，都寫得出一條描述「應有行為」的規則，讓監控器能在違反時報錯。這是**設計上的涵蓋範圍宣稱**。

## Q17：開發者寫自己的系統時，難道要先研究每個變數會流到哪個函式，再全部寫 TAINT 註解？

**不用。** 流向是 ANOTA 自動追的，開發者只要在**來源寫一次**。（依原文 §III-A、§III-B.1、§IV-B.1 核對）

**開發者要寫的**：`TAINT(變數, sanitization=[...], Sink=[...])`，放在敏感資料出現的地方，宣告三件事：
- 哪個變數是敏感的（例：密碼）
- 經過哪個函式處理後就安全（例：`hash`），可省略
- 哪些函式不准收到它（例：`print`），可省略；預設 sink 是 `write()`，即任何寫到不受信任範圍（檔案、網路）的輸出

Listing 2 只有一行：`TAINT($user_credential, sanitization=[hash])`。

**ANOTA 自動做的**：修改過的 CPython 在每個物件上加一個 taint 標記，**每個 opcode 執行時自動傳遞標記**；資料傳進 C 擴充模組時也保留標記（§IV-B.1）。變數被指派、傳參、拼字串、流進哪個函式，都不用開發者追。

論文的立場正是如此：開發者常把 API 當黑箱，不知道內部會怎麼處理資料；ANOTA 的價值在於把「隱含的安全意圖」變成機器能檢查的規則（§VI-B）。

**開發者真正要知道的**：**哪些資料是敏感的、規則是什麼**（意圖），不是資料怎麼流（實作）。

**實際花費**（原文）：
- 作者為 Table III 的應用寫註解，平均每個應用約 60 分鐘（熟悉 ANOTA、但不熟悉該程式碼）；全部共花 10 個工作天。
- 使用者研究：11 位學生 × 6 個應用 = 66 個任務，55 個成功偵測到目標漏洞（83.3%）。
- 受訪者的疑慮：與 CI/CD 整合的成本、註解可能降低程式碼可讀性（§V-D）。

**仍存在的負擔**（推論）：
- 大型系統中「哪些資料算敏感」本身就需要判斷，且要隨程式修改維護註解。
- 上述是 Data Flow（TAINT）的情況；授權類用的 Code Execution 是逐點放置，負擔較大（見 Q13、Q14）。

**與 Y2 的關係**（推論）：ANOTA 的人力花在「寫出意圖」；Y2 的切入點是用 Y1 已打穿的攻擊直接確定「被違反的那一條規則」，減少需要人先寫出意圖的部分。

## Q18：程式怎麼知道哪裡是「誤流出」、該抓出來？

**程式本身不判斷對錯，對錯完全由註解寫的規則決定。** 監控器只做機械比對。（依原文 §III-A、§III-B.1 核對）

**判定規則**：
1. 被 `TAINT` 標記的變數帶上標記，之後每個指令自動傳遞（衍生出的字串、物件也帶標記）。
2. 資料被當作參數傳進宣告的 **sanitization 函式**（例：`hash`）→ 標記清除，視為安全。
3. 帶標記的資料被當作參數傳進**禁止的 sink**（宣告的 sink，或預設的 `write()`，即寫到檔案、網路等不受信任範圍）→ **違規**，監控器通知執行環境，對 fuzzer 而言等同 crash。

**以 Listing 2 走一次**：
```
$user_credential = get_credential(...)        ← 帶標記
TAINT($user_credential, sanitization=[hash])
$hashed = hash($user_credential)              ← 經過 hash，無標記
$log = sprintf("... %s ... %s", $user_credential, $hashed)
                                              ← 拼進了原始密碼，$log 帶標記
file_put_contents("logfile.txt", $log)        ← 帶標記的資料寫檔 → 違規
```
若只把 `$hashed` 寫進 log，`$log` 不帶標記，就不會報。

**所以「誤流出」的定義** = 敏感資料**沒經過宣告的處理**，就到了**宣告禁止的地方**。這是開發者寫下的規則，不是 ANOTA 自己推論出來的。

**程式判斷不了的情況**（推論，論文未逐一討論）：
- **規則寫錯就跟著錯**：漏寫 sink → 抓不到；sink 設太寬 → 合法流出也報（例：預設 `write()` 會把「把密碼送去驗證伺服器」這種正當網路傳輸也算進去，需開發者另行調整）。
- **只認函式名稱**：只要經過 `hash` 就清除標記，不判斷 hash 用得對不對（例如演算法太弱）。
- **只檢查實際執行到的路徑**：fuzzer 沒走到的流向不會被檢查（動態分析的本質）。
- **隱式流**（資料透過 `if` 條件間接影響輸出）是否追蹤，論文未說明，未核對。

**與 Y2 的關係**（推論）：這和 Y2 的處境相同 ——「什麼算錯」需要一條規則。ANOTA 由人寫規則；Y2 由 Y1 的攻擊確定被違反的規則（見 Y2 討論紀錄 Q11）。

## Q19：解釋 Listing 2

（依原文 §III-A Listing 2 與 §III-B.1 說明核對）

**情境**：開發者想在 log 裡記一筆「收到了某個憑證」，卻不小心把**原始憑證**也寫進 log 檔。

```php
1  $user_credential = get_credential($user_id);
2  TAINT($user_credential, sanitization=[hash]);
3  $hashed_credential = hash($user_credential);
4  $log_message = sprintf("credential %s collected with hash %s\n",
                          $user_credential, $hashed_credential);
5  file_put_contents("logfile.txt", $log_message, FILE_APPEND);
```

| 行 | 程式在做什麼 | ANOTA 的反應 |
|---|---|---|
| 1 | 取得使用者的憑證（如密碼） | — |
| 2 | **註解**：標記 `$user_credential` 為敏感；經過 `hash` 處理就算安全。沒寫 `Sink` → 用預設 `write()` | `$user_credential` 帶上標記 |
| 3 | 算出憑證的雜湊值 | 傳進 `hash` → `$hashed_credential` **不帶**標記 |
| 4 | 組 log 字串，**同時放進原始憑證和雜湊值** ← 開發者的錯誤 | 字串含原始憑證 → `$log_message` **帶**標記 |
| 5 | 把 log 字串附加寫入 `logfile.txt` | 帶標記的資料寫進檔案（屬 `write()`）→ **違規** |

**修正寫法**：第 4 行只放 `$hashed_credential`，`$log_message` 就不帶標記，不會報。論文也明說：寫入 `hashed_credential` 不會觸發違規，因為它已經過註解宣告的 `hash` 處理。

**重點**：
- 開發者只寫了第 2 行一行註解，第 3–5 行的流向都由 ANOTA 自動追。
- 違規的定義來自第 2 行的規則：「沒經過 `hash` 的憑證不准寫出去」。

**閱讀時注意**（我的觀察）：
1. **ANOTA 原型只實作 Python**，這段 PHP 是示意，論文沒有在 PHP 上實際執行（見 [ANOTA_論文價值與參考借鑑.md](../ANOTA_論文價值與參考借鑑.md) §措辭須保守）。
2. 論文正文說違規在「line 4」被偵測，但實際寫檔發生在第 5 行；第 4 行只是組字串。依 §III-A 的定義（sink 預設為 `write()`），觸發點應是第 5 行。可能是行號筆誤，或指「錯誤發生在第 4 行」，論文沒有釐清。

## Q21：Listing 3 是針對 Listing 1 的補全嗎？

**不是補全，是「同一個功能加上註解後」的示範。**（依原文 §II-B、§III-A、§III-B 核對）

**Listing 1**（有漏洞的原始程式，§II-B）：
```python
1  def SafeURLOpener(input_link):
2      block_schemes = ["file", "php", "ftp", "data"]
3      block_host = ["youtube.com", "instagram.com"]
4      input_scheme = urlparse(input_link).scheme
5      input_hostname = urlparse(input_link).hostname
6      if input_scheme in block_schemes:
7          return
8      if input_hostname in block_host:
9          return
10     target = urllib.request.urlopen(input_link)
11     print(target.read())
```
漏洞：`urlparse` 對開頭有空白的網址解析錯誤（CVE-2023-24329），輸入 `" https://youtube.com"` 就能繞過第 6–9 行的過濾。

**Listing 3**（加註解的版本）：
```python
1  def SafeURLOpener(inputLink):
2      SYSCALL.NETWORK.BLOCK.SCHEME("file", "php", ...)
3      SYSCALL.NETWORK.BLOCK.HOST("youtube.com", ...)
4      target = urllib.request.urlopen(inputLink)
       print(target.read())
       SYSCALL.NETWORK.CLEAR()
```
- 第 2–3 行：宣告「這段期間，程式不准用這些 scheme、不准連到這些主機」。`...` 是論文省略的其餘清單。
- 結尾 `CLEAR()`：清除網路政策，避免限制到函式外的其他程式（§III-A Annotation Clearing）。

**關鍵差別：檢查發生在哪一層**

| | Listing 1 的過濾 | Listing 3 的註解 |
|---|---|---|
| 檢查什麼 | 程式**自己解析**出來的網址字串 | 程式**實際發出**的系統呼叫（真的連到哪裡） |
| 被 `urlparse` 錯誤影響嗎 | 會 —— 解析錯，過濾就失效 | 不會 —— 不管網址怎麼解析，只看實際連線 |
| 角色 | 正式上線的防護 | 測試時的檢查規則（給 fuzzer 用） |

論文的說法：即使開發者完全不知道底層函式庫有錯，只要加上幾行系統呼叫註解就能偵測；註解讓開發者把「哪些網址該擋」的直覺，變成明確且被監控的政策（§III-B）。

**閱讀時注意**：
1. **Listing 3 印出來時沒有第 2–9 行的過濾程式。** 論文用的詞是「加上」註解，且 ANOTA 是測試工具、不是防護機制，因此較合理的解讀是：原本的過濾程式**仍在**，只是為了版面省略（推論，論文沒有明說）。若理解成「用註解取代過濾」，正式上線時就沒有防護了。
2. Listing 1 的 schemes 有 `ftp`、`data`，Listing 3 只寫出 `file`、`php` 加 `...`，屬省略，不是內容不同。
3. **HOST 政策怎麼在系統呼叫層比對主機名稱**（系統呼叫看到的通常是 IP，不是網域名稱），論文沒有說明（見本紀錄 Q1 註）。

**與 Y2 的對照**（推論）：Listing 1 的錯是「檢查有做、結果也有採用，但**檢查的依據**（`urlparse` 的解析結果）錯了」，不是 Missing Check。它接近收斂文件的 Ineffective Check（「檢查邏輯無效／被旁路」），但**不符合** Y2 README §2.5 較窄的定義（「判定結果未被採用，或存入無人讀取的欄位」）—— 這裡判定結果有被採用。Y2 的失效模式分類可能需要第三類：「檢查依據不可信」。

> **更正（見 Q23）**：上述把 Listing 1 解讀為「檢查依據不可信」是我的延伸，不是論文的說法。論文把原因歸於**函式庫的 bug**（`urlparse` 解析錯誤），開發者的過濾邏輯本身沒有設計錯誤。

## Q22：「檢查依據不可信」是什麼意思？

> **更正（見 Q23）**：本題的例子（請求參數裡的 `userId`、CWE-807）與 ANOTA Listing 1 **不是同一種問題**，是我從 Listing 1 延伸出去的，不能當作論文的例子。

**意思**：檢查**有做**、結果**有採用**，但檢查**拿來判斷的那個值**不可靠 —— 攻擊者能控制它，或它跟後面實際使用的不是同一個東西。所以檢查照樣「通過」，卻擋不到攻擊。

**和其他兩類的區別**（以訂單為例）：

| 類型 | 程式長相 | 問題 |
|---|---|---|
| 缺少檢查（Missing Check） | 直接 `return orderRepo.findById(id)` | 沒有檢查 |
| 檢查無效（Ineffective Check，依 Y2 README §2.5） | 有算 `isOwner`，但後面沒用它 | 結果沒被採用 |
| **檢查依據不可信**（本次提出，暫名） | `if (req.param("userId") == order.ownerId)` | 有檢查、有採用，但 `userId` 是攻擊者自己填的 |

**兩種常見形式**（推論整理）：
1. **依據可被攻擊者控制**：擁有者比對用的是請求參數、header、cookie 裡的使用者 ID，而不是登入 session 的身分。攻擊者填入受害者 ID，檢查就通過。MITRE 有對應類別：**CWE-807「Reliance on Untrusted Inputs in a Security Decision」**（2026-10-12 核對 cwe.mitre.org），子類包含 CWE-302、CWE-784（未經驗證的 cookie）。
2. **檢查的和使用的不是同一個東西**：
   - ANOTA Listing 1：檢查的是 `urlparse` 解析後的結果，實際連線用的是原始字串，兩者對同一個輸入的理解不同。
   - Web 後端例：檢查網址路徑上的訂單 `id` 屬於你，實際更新的卻是請求內容（body）裡的另一個 `orderId`。

**判別方式**：看「檢查讀的值」從哪來、和「後面實際使用的值」是不是同一個。
- 從請求來 → 形式 1
- 跟 sink 用的不是同一個來源 → 形式 2

**對 Y2 的意義**（推論）：
- ② 找缺時，不能只問「路徑上有沒有檢查」，還要追**檢查讀的值的來源**；Y2 已有資料流追蹤（① 的記錄、thin slicing 的正確用途），可以回答這件事。
- 修補建議也不同：缺少檢查 → 加檢查；依據不可信 → **換掉檢查的依據**（改用 session 身分、改用與 sink 相同的值），不是再加一個 `if`。
- 是否把這類正式加入 Y2 的失效模式分類，待侑宸決定。

## Q24：Listing 4、Listing 5 的意思？

（只依原文 §III-B.2、§III-B.3；推論另外標明）

### Listing 4：系統呼叫註解，偵測路徑穿越（JavaScript）

```javascript
1 app.get('/static/:filename', (req, res) => {
2   const file = req.params.filename;
3   const staticDir = path.join(cwd, 'static');
4   SYSCALL.FILE.ALLOW(staticDir);
5   res.sendFile(path.join(staticDir, file));});
```

**論文說的**：開發者想把目前工作目錄下 `static` 資料夾裡的檔案，依請求網址送給遠端使用者；第 4 行的註解確保**跟檔案有關的系統呼叫只能存取參數指定的路徑**；此例用來偵測路徑穿越漏洞。

**白話**（推論，論文未寫出攻擊輸入）：開發者的意圖是「只能讀 `static` 裡的檔案」。第 5 行直接把使用者給的檔名接上路徑，若檔名帶有 `../` 之類的內容，實際讀到的檔案就可能跑出 `static`。第 4 行把意圖寫成規則：只要真的開啟了 `static` 以外的檔案，就違規。

**注意**：ANOTA 原型只實作 Python，這段 JavaScript 是示意。

### Listing 5：存取控制（Python）

```python
1 if is_auth:
2     EXECUTION.BLOCK()
3     user_list.append(new_user)
4     WATCH.ALLOW(user_list, "r")
5     user_list.remove(existing_user) if is_auth else print("not authenticated")
```

**論文說的**：只有一句 ——「只有管理員應該能新增或刪除使用者」。Listing 5 用了兩種註解：Code Execution（第 2 行）與 Object Access（第 4 行）。

**論文沒有說明、我看不懂的地方**（不做推測）：
1. 第 2 行的 `EXECUTION.BLOCK()` **沒有條件參數**，但 Table II 的寫法帶條件（`EXECUTION.BLOCK(user.type != 'admin')`）。沒有條件時代表什麼，論文沒說。
2. 程式檢查的是 `is_auth`（有沒有登入），論文的規則卻是「只有管理員」。是在示範「只檢查登入、沒檢查管理員」這個漏洞，還是 `is_auth` 本身就代表管理員，論文沒說。
3. 第 4 行 `WATCH.ALLOW(user_list, "r")` 放在新增之後、刪除之前：照 §III-A 的定義，此後 `user_list` 只准讀，第 5 行的刪除（寫入）就會違規。但這是否只針對非管理員，論文沒說。

這三點本紀錄 Q2 已記過第 1 點，至今仍無法從原文解決。

### 兩者的差別

| | Listing 4 | Listing 5 |
|---|---|---|
| 註解類型 | System Call | Code Execution ＋ Object Access |
| 守的是 | 程式**實際存取的檔案** | **某段程式**能不能執行、**某個變數**能不能被改 |
| 論文說明的完整度 | 清楚 | 只有一句，多處不明 |

**與 Y2 的關係**（推論）：Listing 5 是論文唯一的存取控制範例，規則是角色層級（管理員 vs 非管理員），不是 BOLA 的「這筆資料是不是你的」（同 Q13）。

## Q26：小結 —— ANOTA 就是一套讓人寫註解的工具，工具在底層攔截實際行為作為判斷依據，準確率較高所以比單元測試好？有漏掉什麼？

**前兩點大致正確，第三點需要修正，另外漏了四件事。**（依原文核對）

### 逐點確認
1. **「讓人編寫註解的工具」→ 對，但只說了一半。** ANOTA = 註解語言 ＋ 執行期監控器，定位是 **fuzzing 用的 sanitizer**（判斷對錯的 oracle）。它**自己不產生輸入**，要搭配 fuzzer（論文用 Atheris），合稱 ANOTA+FUZZER。
2. **「在底層攔截實際行為作為判斷依據」→ 對。** 監控四種行為：系統呼叫（eBPF）、變數讀寫（攔截 opcode）、資料流（taint 傳遞）、程式執行到哪（Code Execution 註解）。違規時讓程式「當掉」，fuzzer 就會把觸發的輸入存下來。
3. **「準確率較高所以比單元測試好」→ 不是論文的說法。**
   - 論文**沒有和單元測試比較**；單元測試只出現在兩處：把專案既有的 test cases 改成 fuzzing harness（§V-A），以及使用者問卷中受訪者目前用的方法（§V-D）。
   - 論文實際的比較對象：
     - **沒有 ANOTA 的 fuzzer**（消融實驗，§V-C）：35 個業務邏輯漏洞，ANOTA+FUZZER 全抓到，單純 Atheris **0 個** —— 即使直接給它會觸發漏洞的輸入也抓不到，因為沒有判斷對錯的依據。
     - **其他工具**（Table VII）：第二名 SonarQube 抓到 18 個（0 誤報），ZAP 17 個。
   - 「跟單元測試比」是**我們自己在 Q3、Q4 討論的**，結論也不是「準確率較高」：就 Listing 1 單一案例，找到那個帶空白的輸入後，單元測試一樣抓得到（Q3）；ANOTA 的優勢在於**一條規則涵蓋所有路徑與輸入**、能抓到**副作用**、能抓到**開發者不知道的錯**（Q4）。

### 漏掉的四件事
1. **知識仍然來自人**：哪些資料敏感、誰能做什麼，要人寫進註解（Table III 的 Info 欄：常數、文件、API 文件）。成本約每個應用 60 分鐘（Q17）。
2. **抓不抓得到取決於 fuzzer 走不走得到**：註解不引導探索；zenml 的漏洞因前置條件太複雜而沒觸發（Q7、Q15）。
3. **成果**：重現 47 個已知漏洞中的 43 個；另找到 22 個新漏洞，取得 17 個 CVE（摘要、§V-B）。〔Table III 實際列數見 Q25〕
4. **限制**：原型只實作 Python；授權類範例是角色層級，不是 BOLA；Code Execution 只守放置的那一點（Q13、Q24）。

### 對 Y2 最重要的一點（推論）
ANOTA 回答的是「**有沒有**違反規則」，**不回答錯在哪一行**（Q20：論文的圖只標規則、不標 bug）。這正是 Y2 要接手的部分。

## Q27：不是說「當掉」是同一團隊前一篇作品（IJON）做的嗎？

**不是。Q7 說的是：IJON 判斷 bug 時「仍靠傳統的 crash」，不是說「讓程式當掉」的機制來自 IJON。** 兩篇的「當掉」意思不同。（依原文核對）

| | IJON（同團隊先前作品） | ANOTA |
|---|---|---|
| 註解的用途 | **引導** fuzzer 探索更深的程式狀態 | **定義**什麼算違規 |
| 「當掉」從哪來 | 程式**自己**因 bug 當掉（例如記憶體錯誤）；IJON 只是拿來當 bug 訊號 | **ANOTA 刻意製造的**：違反規則時，監控器送訊號給直譯器，直譯器**主動觸發 segmentation fault** |
| 為何需要 | 記憶體類 bug 本來就會當掉 | 業務邏輯漏洞**不會**自己當掉，只好人為讓它當掉，fuzzer 才看得到 |

**原文依據**：
- §VII：IJON 用註解引導 fuzzer 到更深的狀態，但仍依賴傳統的 bug oracle（例如 crash），而不是偵測新的漏洞類型。
- §III：policy monitoring module 把違反政策**升級**成 fuzzer 能偵測的 crash。
- §IV-B：偵測到違規時，送訊號回直譯器，**直譯器觸發 segmentation fault**。
- §I：ANOTA 可搭配任何既有 fuzzer，方式通常是把違反政策回報成程式 crash。

**所以 Q26 說「違規時讓程式當掉」是 ANOTA 自己的機制，沒有錯。** Q7 的寫法把兩件事放在同一段，容易讀成「當掉是 IJON 的」。

## Q28：怎麼覺得 IJON 反而比 ANOTA 更有價值？

**要看用什麼標準。兩篇解決的是 fuzzing 的不同半邊，不是同一件事做得好壞。**

**IJON 是什麼**（依搜尋到的摘要；會議為 IEEE S&P 2020 是我的記憶，搜尋結果未顯示會議名稱）：Aschermann、Schumilo、Abbasi、Holz（波鴻魯爾大學）。讓人用通常一行的註解，把程式內部狀態告訴 fuzzer，幫它探索到原本到不了的深層狀態；例如讓 fuzzer 玩通 Super Mario Bros.，並解出 CGC 資料集中先前自動與人工方法都解不開的題目。

| 標準 | IJON 較強 | ANOTA 較強 |
|---|---|---|
| 解決的問題 | **走得到**：讓 fuzzer 到達深層狀態 | **看得出**：讓 fuzzer 知道什麼算錯 |
| 成熟度與影響 | 較早發表；已有後續工作延伸（SandPuppy 自動找狀態變數套用 IJON 式註解；AIJON 2026 用 LLM 產生 IJON 註解） | 2026 新作；原型只有 Python；評估有疑點（Q25）；Listing 5 說明不清（Q24） |
| 能否偵測業務邏輯漏洞 | **不能**：仍靠傳統 crash 判斷 bug（§VII），邏輯漏洞不會當掉 | **能**：消融實驗中，fuzzer 即使拿到觸發輸入也 0/35，加上 ANOTA 才 35/35 |

**兩者互補**（推論）：ANOTA 抓不到 zenml 的漏洞，原因正是「走不到」（Q7）—— 這是 IJON 要解的問題。反過來，IJON 走到了業務邏輯漏洞的狀態，也看不出那是錯的。ANOTA 論文本身沒有討論結合兩者（未核對全文是否提及）。

**IJON 也不是無條件有效**：AIJON（2026）的作者報告，在 Magma 基準上，基於註解的 fuzzing 並沒有嚴格優於 AFL++（依搜尋摘要，未讀原文）。

**對本計畫**（推論）：
- **Y1**：業務邏輯漏洞常需要多步驟才能到達（先建立 A、再邀請 B、B 再改 A 的資料，如 zenml），IJON「幫 fuzzer 走到深層狀態」的想法可能和 Y1 較相關，由祐廷判斷。
- **Y2**：兩篇都不是定位工具。ANOTA 的「規則／oracle」概念較接近 Y2 要寫出的「被違反的規則」；IJON 對 Y2 的直接價值較低。

**結論**：作為研究貢獻，IJON 較成熟、影響較確定，這個感覺有根據；但對「業務邏輯漏洞」這個問題，IJON 單獨使用偵測不到任何東西，ANOTA 處理的 oracle 問題是必要的那一半。

## Q29：一篇用註解引導 fuzzer、一篇用註解判斷對錯，怎麼反而是第二篇比較有價值？

**Q28 沒有說 ANOTA 整體比較有價值。** Q28 的結論分兩層：作為研究貢獻，IJON 較成熟、影響較確定；只針對「業務邏輯漏洞」這個問題，ANOTA 處理的是**缺了就完全不能用**的那一半。（另：ANOTA 的註解是判斷「**程式**有沒有違規」，不是判斷「fuzzer 失效」。）

**為何對業務邏輯漏洞來說，「判斷」是瓶頸**（依原文數據）：
- **只能走、不能判斷 → 抓到 0 個**：消融實驗中，Atheris 即使**直接拿到觸發漏洞的輸入**，35 個也一個都沒報（§V-C）。走到了，也看不出錯。
- **能判斷、只靠普通的走法 → 大多抓得到**：ANOTA 搭配**沒有任何引導**的 Atheris，基準 35/35，真實漏洞重現 43/47；沒抓到的 4 個中，只有 zenml 是因為走不到（另 3 個是沒寫註解、權限系統太複雜不會寫、需特定設定，§V-A）。

所以在論文的評估裡，缺的是判斷，不是探索。

**但這個結論有前提**（推論）：
- 論文的基準是故意寫爛的教學用應用（Pygoat、DSVW 等）和 Python 套件，**狀態大多很淺**，普通 fuzzer 就走得到 —— 這會讓「判斷」顯得比「探索」重要。
- 真實系統的業務邏輯常需多步驟才觸發（zenml：A 建邀請連結 → B 註冊 → B 改 A 的密碼）。在這類系統中，**探索可能才是瓶頸**，IJON 那一半就變得關鍵。
- 哪一半是瓶頸，取決於目標系統，論文的資料無法回答。

**整理**：
| 情況 | 瓶頸 | 較關鍵的一篇 |
|---|---|---|
| 狀態淺、單一請求就能觸發 | 判斷 | ANOTA |
| 狀態深、需多步驟才觸發 | 探索（同時仍需判斷） | 兩者都要 |
| 記憶體類 bug（本來就會當掉） | 探索 | IJON |

## Q30：ANOTA 就是三個部分（程式本身、fuzzer、判斷有沒有問題）？那 fuzzer 豈不是略顯多餘？

**三個部分大致對**，補充細節（依原文）：

| 部分 | 內容 |
|---|---|
| 被測程式 | 開發者把註解寫進原始碼；另用專案既有的 test cases 改成 fuzzing 入口（harness，§V-A） |
| Fuzzer | Atheris；Web 應用另加 custom mutator（集中變異 cookie、query 參數、header、URL）與惡意 payload 字典（§V-A） |
| 判斷（Policy Monitor） | 修改過的 CPython ＋ eBPF，監看執行時的行為，違規就觸發 segmentation fault（§IV） |

**fuzzer 不多餘：監控器只能判斷「已經發生的執行」，要有人產生輸入讓程式跑起來。** 註解不會告訴你哪個輸入能觸發漏洞 —— 例如 Listing 1 那個開頭帶空白的網址，是 fuzzer 變異出來的，不是註解提供的。

**為何會覺得多餘**：
1. 消融實驗顯示「只有 fuzzer → 0/35」，容易讓人覺得功勞全在判斷那一半。但反過來，「只有判斷、沒有輸入」也是 0 —— 什麼都沒執行，就什麼都判斷不了。
2. Q3 已討論過：**如果已經知道觸發輸入，就不需要 fuzzer**，寫一個單元測試餵那個輸入即可。fuzzer 的價值在於**找出事先沒想到的輸入**。

**論文中 fuzzer 確實有在做事的證據**：
- 22 個新漏洞：事先沒有人知道觸發輸入。
- 重現已知漏洞時，負責評估的作者**只知道漏洞類型**，不看漏洞報告（§V-A），觸發輸入要靠 fuzzer 重新找出來。

**另外，fuzzer 不是完全「普通」的**：Web 應用用了 custom mutator 和 payload 字典，這些設計讓觸發更容易，但與註解無關（Q7）。

**與 Y2 的關係**（推論）：Y2 正是「**已經有觸發輸入**」的情況 —— Y1 打穿的攻擊請求就是那個輸入。所以 Y2 不需要 fuzzer，剩下的問題是 ANOTA 留給人的兩件事：**規則是什麼**、以及 ANOTA 不回答的 **錯在哪裡**。

| SonarQube | static | **SAST** | 原始碼品質與安全掃描 |
| Pysa（Meta） | static | **SAST** | 靜態污點分析，需設定 source/sink |
| ZAP（Zed Attack Proxy） | dynamic | **DAST** | 黑箱 Web 掃描器，從外部送請求 |
| Wapiti | dynamic | **DAST** | 黑箱 Web 掃描器 |
| Atheris | （消融實驗的基準 fuzzer） | 都不算 | 覆蓋率導向的灰箱 fuzzer，要在程式內部掛 harness，不是從外部掃描的 DAST |
| ANOTA+FUZZER | — | 都不算 | 在程式**內部**監控執行行為，概念上接近 IAST（互動式應用程式安全測試）—— 此為我的對應，論文沒有用這個詞 |

**比較條件**（附錄 A）：
- 靜態工具有提供**與 ANOTA 註解等量的 source/sink 資訊**；但沒有做「整個專案的型別標註」這類設定（如 Pysa 需要的），作者認為那樣的成本遠超過 ANOTA。
- Pysa、ZAP 依官方文件設定時，需要大量人工定義 source、sink、存取規則。

**論文對結果的解釋**：
- SAST（Semgrep、Pysa）：缺少執行期資訊，漏報多。
- DAST（ZAP、Wapiti）：受黑箱限制、程式碼覆蓋淺；ZAP 無法區分讀與寫權限，因此漏掉數個漏洞。

## Q33：為何 DAST 不像 ANOTA+FUZZER 那樣從內部看，而只能從外部看？

**因為「只從外部看」就是 DAST 的定義，是刻意的取捨，不是做不到。** 從內部看的工具另有名稱（IAST、灰箱 fuzzing），就不叫 DAST 了。（以下為一般知識整理，非 ANOTA 論文內容）

| | DAST（ZAP、Wapiti） | 從內部看（ANOTA+FUZZER、IAST） |
|---|---|---|
| 需要什麼 | 只要一個跑起來的網址 | 原始碼或執行環境的控制權；要在程式裡裝監控 |
| 能測誰的系統 | 任何語言、任何框架、甚至別人的系統 | 只能測自己能改的系統；ANOTA 還限定 Python，且要換成修改過的直譯器 |
| 看得到什麼 | 只有回應：狀態碼、回傳內容、時間 | 程式內部：呼叫了什麼、讀寫了哪個變數、資料流到哪 |
| 判斷依據 | 回應有沒有異常特徵（錯誤訊息、注入成功的痕跡） | 內部行為有沒有違反規則 |
| 弱點 | 業務邏輯漏洞常回傳正常的 200，從外面看不出錯；也分不出讀與寫權限（ANOTA 附錄 A 對 ZAP 的觀察） | 部署成本高，綁定特定語言與執行環境 |

**為何要選外部**：DAST 的用途是在**拿不到或不想動程式碼**時測試，例如測第三方系統、測已部署的環境、資安人員做滲透測試。為了這個適用範圍，放棄了內部可見度。

**與本計畫的對應**（推論）：
- **Y1 是黑箱**，處境就像 DAST —— 只看得到外部回應，所以「這算不算攻擊成功」對業務邏輯漏洞特別難判斷。
- **Y2 是白箱**，能從內部看 —— 這正是 Y2 能回答「錯在哪一行」的前提。
- 三年的分工，某種程度就是「外部看到現象（Y1）→ 內部找出原因（Y2）→ 修正（Y3）」。

## Q34：既然要和 SOTA 比較，為何不給更公平的比較環境？

**論文自己給的理由**（§V-C，已核對原文）：
- **沒有同類的 sanitizer** 可以直接比。
- **其他 fuzzer 不適合**：只針對單一漏洞類型（EDEFuzz、CTFuzz、SSRFuzz）、需要無法滿足的前提（EDEFuzz 需要 GUI、FLOWFUZZ 需要完美重置），或依賴無法跨語言的啟發式方法（Atropos 只做 PHP、ODDFuzz 只做 Java）。
- 因此改和「最相關的靜態與動態漏洞掃描器」比。

**論文做的公平化措施**（附錄 A）：靜態工具給了與註解等量的 source/sink 資訊；各工具依官方文件設定，Pysa、ZAP 花了大量人工定義規則。

**仍然不公平的地方**（我的評論）：
1. **資訊量不對等**：ANOTA 從程式內部看，還有人寫的規則；DAST 只能從外部看。結果證明的是「內部視角＋人寫規則」勝過「外部視角」，這是可預期的，不能證明 ANOTA 的設計本身比較好。
2. **註解是對準漏洞寫的**：附錄 A 原文說 ANOTA「只註解與漏洞相關的程式碼段」—— 寫註解的人知道 35 個漏洞在哪。靜態工具拿到等量的 source/sink，但 DAST 拿不到這種位置資訊。
3. **缺少最接近的對照組**：
   - **Atheris＋人工寫的 assert**：同樣的 fuzzer、在同樣位置寫普通的 Python `assert`。這最能回答「ANOTA 的註解系統比直接寫 assert 多了什麼」，論文沒做。
   - **IAST 工具**：同樣從內部看的商用／開源工具，論文沒提。
4. **消融實驗的對照組必然是 0**：沒有 oracle 的 fuzzer 本來就看不出邏輯漏洞，0/35 是設計上的必然，不是實驗發現（本紀錄 Q4 已記）。

**論文沒有討論**為何不設計上述對照組。

**對 Y2 的提醒**（推論）：Y2 設計評估時要避開同樣的問題 —— 對照組要拿到**同等的資訊**（例如給 INTENTFIX 類方法同樣的攻擊紀錄），並設計「最便宜的替代方案」當對照組（例如直接把攻擊請求和程式碼丟給 LLM 問錯在哪），才能證明 Y2 的方法本身有貢獻。

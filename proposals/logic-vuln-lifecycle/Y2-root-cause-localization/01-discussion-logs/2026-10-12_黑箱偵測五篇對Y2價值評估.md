## Q1：Pellegrino、DetLogic、AuthScope、A2CT、BACScan 對 Y2 有幫助嗎？

**結論：五篇都是黑箱「偵測」工具，主要服務 Y1；對 Y2 不是核心技術來源。** Y2 的前提是漏洞已被 Y1 打穿，要回答的是「程式碼哪裡少了什麼檢查」，這五篇都停在 HTTP 層，不碰程式碼。

| 論文 | 出處 | 做法（摘要層級） | 主要服務 | 對 Y2 價值 | 能借到 Y2 哪一步 |
|---|---|---|---|---|---|
| Pellegrino & Balzarotti | NDSS 2014 | 從正常使用者的網路流量推導行為模式，再產生攻擊測資；7 個電商網站找到 10 個漏洞 | Y1 | 低 | 2-1 寫「被違反的規則」時，可參考其行為模式分類 |
| DetLogic（Deepa et al.） | JNCA 2018（期刊，vol. 109） | 把預期行為建成帶註解的有限狀態機，導出參數、存取控制、工作流程三類約束，再故意違反 | Y1 | 低–中 | 2-1：三類約束可對應「資源／動作／必須滿足的條件」的規則格式 |
| AuthScope（Zuo, Zhao, Lin） | CCS 2017 | 行動 App 對伺服器的流量，雙帳號差分替換欄位，找出未綁定使用者的授權欄位 | Y1 | 低 | 2-1／3-1：先確定哪個請求參數是「資源識別碼」，再從它追到資料庫存取點 |
| A2CT（Schlaubitz, Veyisoglu, Rennhard） | ICISSP 2025 | 多帳號爬取並交叉重放所有 HTTP 方法的請求，涵蓋功能層與物件層存取控制；30 個網站、14 個新漏洞、開源 | Y1 | 低 | ④ 4-3「重送正常使用者請求」的設計可參考其多角色重放 |
| BACScan（Liu, Zhang et al.） | CCS 2025 | 回饋式 oracle：找出會顯示被修改資料的頁面，攻擊者重放修改請求後回頭檢查該頁；20 個網站、89 個漏洞、35 個 CVE | Y1 | **中** | ④ 4-4 判讀：修改型操作（INSERT/UPDATE/DELETE）**看回應判斷不出來** |

### 對 Y2 最有用的一點：BACScan 的 oracle 問題

BACScan 指出，修改型操作光看回應無法判斷是否成功越權（其摘要報告的回應相似度判斷誤報／漏報率很高）。這直接影響 Y2 第 ④ 步：

- 4-4 判讀「攻擊被擋」時，**不能只看 HTTP 回應碼或內容**，對修改型操作要看資料庫狀態是否改變。
- Y2 第 ① 步本來就記錄實際執行的資料庫查詢，所以可以比 BACScan 更直接：插入檢查後重送攻擊，確認那條 `UPDATE`／`DELETE` 沒有被執行。這是白箱相對於黑箱的優勢，可寫進論文的 Y2 差異點。

### 另一個用途：相關研究的對照組

五篇共同的限制是「只能告訴你哪個網址有洞，不能告訴你程式碼哪裡缺檢查、還有哪些入口共用同一個缺口」。這正是 Y2 第 ②、③ 步的定位，可以集中寫成一段相關研究，用來論證 Y2 的必要性。

### 比這五篇更貼近 Y2 的方向

同為存取控制，但屬於**白箱**、直接分析程式碼的：

- **MACE**（CCS 2014）、**Sun et al.**（USENIX Security 2011，靜態偵測存取控制漏洞）：已列在風險矩陣文件的參考文獻 [^10]、[^12]。
- 這兩篇看程式碼裡的授權檢查，比上面五篇更接近 Y2 的「找缺」。

## Q2：附的第 2 點聽不懂

文件用註腳引用：正文某句後面寫 `[^10]`，代表這句的根據是第 10 號文獻，文件最下面再列出第 10 號是哪篇。問題是有些文獻**只列在最下面，正文沒有任何一句引用它**。後果：

1. 讀者不知道為什麼列這篇，看不出哪個設計決策是根據它做的。
2. GitHub 預設不顯示沒被正文引用的註腳，網頁上可能直接消失。

處理方式只有兩種：在對應的句子補引用，或從參考文獻刪掉。

## Q4：那 BACAgent 呢？

> **出處**：本題依據作者頁公開的全文 PDF（Liu et al., *BACAgent: LLM-Powered Detection of Broken-Access-Control Vulnerabilities in Web Applications*, CCS 2026, DOI 10.1145/3830454.3832642），逐節閱讀。repo 內尚無筆記。

**結論：和前五篇完全不同。BACAgent 是白箱、看原始碼，而且是目前和 Y2 最接近的對手，對 Y2 價值高。** 名稱裡的 Agent 指的是用 LLM 代理推論，不是黑箱滲透 Agent。

### 它在做什麼

作者群與 BACScan、MOCGuard 相同（復旦 Yuan Zhang 組）。核心問題：**「這個資源本來該受什麼存取控制？」**（論文稱 intended ACP）。三階段：

1. **辨識既有檢查**（§4.1）：
   - 框架型：先列出 Spring Security、Shiro、Java EE Filter 等框架的授權 API（Table 1），靜態找出呼叫點，再用 RAG 查框架文件，讓 LLM 判斷「檢查的是哪個角色」。
   - 自訂型：列出取得目前使用者的 API（`HttpSession`、`SecurityContext`、`ThreadLocal`、JWT 等，Table 2），用資料流找出「使用者資料流進 if 條件」的判斷，再讓 LLM 分類為角色檢查（VAC）或擁有者檢查（HAC）。擁有者檢查要求另一邊來自資料庫的 owner 欄位。
2. **推論應有的規則**（§4.2）：規則是四元組 `<資料表, 操作, 角色, 應有檢查>`，例如 `<Order, Read, User, HAC+VAC>`。證據來自既有檢查、資料庫 schema（表名、欄名、外鍵）、API 路徑與註解。先給高信心證據，不夠再按需補（on-demand），避免一次塞太多讓 LLM 分心。
3. **比對**（§4.3）：沿「使用者輸入 → 資料庫操作」路徑收集實際執行的檢查，和規則比對，不一致就報漏洞。

成效：30 個應用（Java、PHP、Go 各 10），157 個漏洞（65 個新），precision 78.89%、recall 86.79%；規則推論抽樣 200 筆正確率 94.5%。比 PCFinder、MOCGuard、BolaRay 都好。程式碼已開源（論文參考文獻 [23]：github.com/LFYSec/BACAgent）。

### 對 Y2 哪裡有用

| Y2 步驟 | BACAgent 可借的部分 |
|---|---|
| 2-1 寫出被違反的規則 | 四元組 `<資料, 操作, 角色, 應有檢查>` 幾乎就是 Y2 的「資源／動作／必須滿足的條件」，可直接採用或對齊格式 |
| 2-2 列出路徑上的檢查 | 框架 API 清單（Table 1）、取得使用者的 API 清單（Table 2）、「使用者資料流進 if」的找法、RAG 解讀框架註解，可直接用在風險矩陣文件 DR-11 守衛辨識 |
| 2-2 無鄰居時 | 它用資料庫 schema 與命名推論規則，不依賴「多數地方寫對」，可補 MACE 式同儕比對的弱點 |
| 3-1 找所有入口 | 它以資源（資料表）為中心收集所有存取路徑，和 Y2 從資料庫存取點往回找入口的方向一致 |

### 它和 Y2 的差異（Y2 的立足點）

BACAgent 自己承認的失敗原因，剛好是 Y2 的輸入能解決的：

| BACAgent 的問題（§5.2、§5.3） | Y2 為何不會有 |
|---|---|
| 21 個誤報來自規則推論錯，把公開資源當成要擁有者檢查 | Y2 的規則由 Y1 實際打穿的攻擊決定，漏洞存在是已知事實，不用猜 |
| 18 個漏報來自反射等間接呼叫，使污點分析中斷 | Y2 有執行紀錄，實際走的路徑是觀察到的，不用靜態推 |
| 14 個誤報來自 lambda 等寫法沒認出既有檢查 | Y2 第 ④ 步實際插入檢查重送，可驗證判斷 |
| 只報「哪裡有漏洞」，驗證靠人工在本機重現 | Y2 輸出補在哪一層、替代位置、優先順序，並自動驗證 |
| 只處理存取控制（VAC／HAC） | Y2 七欄另有工作流順序、一次性、數值完整性、條件適用性 |

**風險**：BACAgent 已經做到「推論規則 + 沿路徑比對既有檢查」，Y2 若只做存取控制、只靠靜態比對，會被視為 BACAgent 的子集。Y2 的論述必須放在「由攻擊確定規則」「執行紀錄消除路徑歧義」「動態驗證」「修補位置決策」與「存取控制以外的業務邏輯」。

### 論文引用中值得追的線索

- **PCFinder**（Shi et al., IEEE TIFS 2025）：Java Web 應用的權限檢查辨識，與 DR-11 直接相關。
- **RoleCast**（Son et al., OOPSLA 2011）：不知道檢查長什麼樣時找缺失檢查。
- **FixMeUp**（Son et al., NDSS 2013）：修補存取控制錯誤，與 Y3 相關。
- **Lu et al.（CCS 2022）**，*Detecting Missing-Permission-Check Vulnerabilities in Distributed Cloud Systems*：分散式雲端系統的缺失權限檢查（工具名稱未從參考文獻確認）。

（以上四篇書目取自 BACAgent 參考文獻，尚未逐篇核對。）

## Q5：AuthScope 呢？

> **出處**：本題依據 CCS 2017 會議公開的全文 PDF（acmccs.github.io/papers/p799-zuoA.pdf）逐節閱讀。Q1 表中的描述原為摘要層級，經全文核對無誤，評價由「低」調整為「低～中」。

**結論：仍是 Y1 的工具，但讀完全文後有三個具體可借給 Y2 的設計。**

### 它在做什麼（§3–§4）

完全黑箱：不看伺服器程式碼，只看 Android App 與伺服器之間的流量。

1. **自動登入**：用 Facebook 登入繞過註冊，事先註冊兩個帳號 Alice、Bob，以固定順序的 DFS 走過 App 畫面，讓兩人產生相同順序的請求。
2. **找出欄位**：
   - Alice 與 Bob 的同一個請求對齊比較，值不同的就是「跟使用者有關的欄位」（例如 UID、token）。
   - **Alice 自己登入登出兩次**，同一請求再比一次，值不同的是時間戳之類的雜訊欄位，予以排除。
   - 只替換「猜得到」的欄位：數值距離小於 App 下載量的（如 21690 對 21691），或是 email、Facebook ID 這類可公開取得的值；隨機 token 不換。
3. **判斷**：保留 Alice 的 token，只把欄位換成 Bob 的值重送；去掉雜訊欄位後，回應若和 Bob 自己的回應完全相同，就是漏洞。
4. **排除公開資源**：再跑一次「不登入」，若同一介面不登入也拿得到同樣內容，就不算漏洞。

成效：4,838 個 App，替換 57,736 個欄位，得到 2,976 個可疑介面，**其中 2,379 個（約 80%）是公開資源**，最後確認 597 個漏洞、對應 306 個 App。限制（§7）：只能偵測越權讀取，越權寫入無法判斷；只支援 Facebook 登入的 App。

### 可借給 Y2 的三點

| 借什麼 | 對應 Y2 哪裡 | 說明 |
|---|---|---|
| **同一使用者重跑一次，濾掉雜訊** | 風險矩陣文件 D2（攻擊與正常執行的分支差集）、§6 未決問題 3 | 比對攻擊紀錄和正常紀錄時，時間戳、快取、隨機數也會造成分支差異。照 AuthScope 的作法，正常請求重跑兩次，兩次之間就不同的分支先排除，剩下的差異才是候選 |
| **只換資源識別碼、保留攻擊者身分** | 風險矩陣文件 D3（換身分看檢查結果變不變） | 前一份紀錄已指出 D3 在攻擊紀錄上會恆成立。AuthScope 的對照設計正好提供改法：固定「攻擊者 token ＋ 受害者資源 ID」這組攻擊請求，對照「受害者 token ＋ 受害者資源 ID」的正常請求，只讓身分這一個變數不同，再看守衛判定是否改變 |
| **公開資源是誤報主因（約 80%）** | Y1→Y2 交接、2-1 寫規則 | 與 BACAgent 的觀察一致（其 21 個誤報來自把公開資源當成需要擁有者檢查）。Y1 若以回應相似度判斷成功，可能把公開資源交給 Y2。Y2 在 2-1 寫規則前應先確認「這個資源本來就該受保護」，例如用不登入或第三個帳號重送一次 |

### 不適用的部分

- 自動登入、畫面探索、欄位猜測性判斷都是為了**找**漏洞，屬 Y1 範圍。
- 它的「根因」停在協定層（用了可預測 ID、email、Facebook ID 當授權依據），沒有對應到程式碼位置。

### 對風險矩陣文件引用的影響

Q3 曾以「正文未使用」刪除 [^11] AuthScope，並說明 D3 改寫時再決定是否加回。依本題，D2 雜訊過濾與 D3 對照設計都可以 AuthScope 為依據，**待 D2、D3 改寫時一併加回引用**。

## Q1：程式碼本來就是沒有 `if (訂單擁有者 != 目前使用者) 拒絕` 才有問題，為何還會被 thin slicing 砍掉？

有漏洞的那段確實沒有這行，所以沒東西可砍。**被砍掉的是拿來對照的正常程式碼。**

要知道「少了」，得拿旁邊有檢查的網址來比：

```java
// 取消訂單（正常的）
public void cancelOrder(Long id) {
    Order o = repo.findById(id);
    if (!o.getOwner().equals(currentUser)) throw new Forbidden();  // ← 有檢查
    o.cancel();
}

// 查看訂單（有漏洞的）
public Order getOrder(Long id) {
    Order o = repo.findById(id);
    return o;                                                      // ← 沒檢查
}
```

thin slicing 只保留「資料怎麼傳」的行，會刪掉 `if` 這種「決定要不要往下走」的判斷。瘦身後兩個網址看起來都沒檢查，比較不出差異。

**修法**：thin slicing 只用來追資料流向（例如 `id` 是否直接來自網址參數）；找檢查時另用方法，保留所有 `if`。

## Q3：一個對照網址把檢查寫在 controller、另一個寫在 service，聽誰的？

分兩個問題：

**判斷「有沒有少檢查」時：兩個都算。** 比的是從入口到資料庫的整條路上有沒有檢查，不是寫在哪一層。

```
網址 A：Controller(✅) → Service → 資料庫      → 有檢查
網址 B：Controller → Service(✅) → 資料庫      → 有檢查
網址 C：Controller → Service → 資料庫          → 整條都沒有 ← 可疑
```

這也是設計文件以「整條路徑」而非「單一函式」當一列的原因。

**回報「該補在哪」時：要選，不建議兩層都加**（兩層都加屬縱深防禦，不算錯，但增加維護成本）。判斷順序見 Q4。

評估時，修補紀錄改在任一合理位置都應算 Y2 找對 → 「正確答案」要事先定義成一組可接受位置。

## Q4：如果專案本身都把邏輯寫在 controller 呢？

**跟著專案習慣，建議補在 controller。**

- 工程師比較會照著修
- 真實修補紀錄幾乎會照習慣寫，評估比對較準

習慣用數的：同種資料的 10 個網址裡 9 個寫在 controller → 習慣是 controller。

**例外**：一個 service 被兩個 controller 共用，且兩個都沒檢查 → 照習慣就要**兩個 controller 都補**，並列出替代方案「補在 service 一次涵蓋」。這對應收斂文件步驟 3：「由被攻擊的 Sink 沿呼叫圖逆流而上，搜尋全專案共享該約束的所有危險進入點」。

## Q5：要 Y3 自己判斷修 controller 還是 service？

**不是。由 Y2 給出明確建議並附理由。** 判斷所需的資訊（專案習慣、共用關係、同樣的洞在哪）都是 Y2 已做完的分析，不該讓 Y3 重做。

| | 負責 |
|---|---|
| 哪裡出錯、為什麼出錯 | Y2 |
| 建議補在哪一層（附理由） | Y2 |
| 實際修補程式碼 | Y3 |
| 照建議修了卻出問題，要不要改位置 | Y3 可推翻，但要說明理由 |

Y2 輸出範例：

> 建議位置：`OrderController.getOrder()`、`OrderController.exportOrder()`
> 理由：專案 9/10 的 Order 端點把檢查寫在 controller；兩者共用 `OrderService.getOrder()`，且皆無檢查
> 替代位置：`OrderService.getOrder()`（一次涵蓋，但不符專案慣例）

## Q6：找路、找缺、找範圍、驗證分別要如何做？

## Q7：① 的「在測試環境啟動目標網站」是否應參考 FORGE？

**不建議。** FORGE（arXiv 2606.03453，2026/06 單一作者預印本，未經同儕審查）不重建原專案，而是另寫一個只嵌入漏洞套件的極小網站（§3.1），作者自承缺少 authentication 等真實系統複雜度（§5.2）。

| Y2 需要 | FORGE 環境 |
|---|---|
| 鄰居網址 | 新網站只有一兩個網址 |
| 專案的檢查習慣 | 非原專案，無習慣可數 |
| 擁有者檢查 | 無登入、無權限機制 |

其 OpenTelemetry 記錄到 HTTP 請求、指令、檔案存取層級，未提方法呼叫或 SQL（§1）；也沒有授權類 CWE 的結果。

- 較合適的參考：CVE-GENIE（`raw-papers/2026/`），從有漏洞版本的原始碼重建原專案。細節（如 Java 成功率）待讀。
- 更根本：Y1 攻擊成功時必已跑起目標網站 → 1-1 應優先沿用 Y1 的環境（併入待辦）。
- 可借鑑：建置→部署→測試＋防造假檢查的流程；攻擊時同步收集 trace。

## Q8：什麼叫鄰居網址？

同一網站裡處理**同一種資料**的其他網址。例：`/orders/123`（查看）、`/orders/123/cancel`（取消）、`PUT /orders/123`（修改）彼此是鄰居。用途是看「別人怎麼做」：別人都有擁有者檢查、只有它沒有 → 可疑。

## Q9：如果專案全部沒寫身分驗證，或只有一個網址有寫，是不是就測不到？

**只靠鄰居的話，是。** 這是同儕一致性方法（MACE、ACMiner）的共同弱點：前提是「大多數地方寫對」。

但 Y2 有兩個偵測工具沒有的條件：
1. **已知一定有洞**（Y1 攻擊成功），只需回答「洞在哪」。
2. **不靠鄰居的直接證據**：資料表有 `user_id` 但攻擊時 SQL 沒用到（BolaRay 作法）；網址參數直接流進查詢；攻擊與正常請求走同一條路。

全專案都沒寫 → 仍找得到缺什麼，結論是系統性缺失；「補在哪層」無習慣可依，用預設規則。精準度會下降，提案需列為已知限制並統計其出現頻率。

## Q10：確定還要以鄰居為參考？立得住腳嗎？

**作為主要依據立不住，只適合輔助。** 理由：間接證據（依賴「多數寫對」）、雜訊多（公開網址本就不需檢查）、審稿人會視為 MACE 重做。Y2 的優勢是攻擊紀錄，直接證據只關於這條路本身。

直接證據的弱點：擁有關係可能間接（留言→文章→作者）；目前登入者可能經框架間接取得，資料流追不到；工作流程類漏洞不涉及擁有者欄位，需另行設計。

## Q11：為何不先建立一個預期權限模型？

**立場更正（回應「不要我說一個你就對」）**：

- 前一輪列的直接證據（「有 `user_id` 卻沒用」）**本來就是拿一個隱含的預期模型在比對**。把模型講明確是更好的表達，不是推翻先前想法。上一輪回答「你說得對、是我偏離了」屬於附和過頭。
- **不同意「先建整個網站的權限模型」**：那是偵測工具的範圍，對 Y2 不必要且成本高。Y2 只需寫出**這個資源、這個動作被違反的那一條規則**，Y1 的攻擊已確定是哪條。
- 鄰居比對的失效條件應在一開始就主動說明，不該等被問 —— 這是真正的疏漏。
- 不變的部分：四步流程；以 Y1 攻擊紀錄為起點；證據來自資料庫結構、資料流、攻擊/正常比對；以臨時插入檢查驗證。

規則來源（依可靠度）：Y1 的攻擊 ＞ 資料庫結構 ＞ Spring Security 設定與註解 ＞ 鄰居 ＞ LLM 推論（需人工確認）。每條規則須標來源。

INTENTFIX 的 `(D, A, R, P, SC)` 即為此類規則格式（[INTENTFIX_論文核心技術解讀.md](../INTENTFIX_論文核心技術解讀.md) §2），擴展文獻指南 A.2 亦已將其列為核心挑戰。

## Q12：所以 INTENTFIX 對 Y1 比較有幫助？

**不是，對 Y1 關係最弱。** INTENTFIX 三階段：讀原始碼推意圖 → 比對程式碼找缺 → 產生修補。

| | 關係 | 原因 |
|---|---|---|
| Y1 | 最弱 | Y1 是黑箱，INTENTFIX 前兩階段都要讀原始碼 |
| Y2 | 對標＋工具 | 第 2 階段即 Y2 的工作；收斂文件定為頭號對標；`SC` 可作規則格式 |
| Y3 | 最直接 | 第 3 階段即修補（此為本次判斷，筆記未記載） |

Y2 的差異：INTENTFIX 的意圖是 LLM 猜的、且限單一檔案；Y2 有攻擊紀錄錨定被違反的規則，並跨檔案追呼叫鏈。

**提議（未驗證、未與組員討論）**：以 `SC` 作為三年共用交接格式 —— Y1 輸出被違反的 SC，Y2 輸出哪裡沒執行該 SC，Y3 輸出讓程式執行該 SC 的修補。

## Q14：為何流程還在找鄰居？到底應不應該用鄰居？

流程未改是因為先前提案尚未定案。**決定：要用，但不用來判斷「缺了什麼」** —— 「缺了什麼」由 Y1 的攻擊確定（被違反的規則）。

| 用途 | 為何非鄰居不可 |
|---|---|
| 辨識專案自訂的檢查方法 | 鄰居都呼叫 `checkAccess()` 才知道它是檢查 |
| 決定補在哪一層 | 團隊習慣只能從其他網址統計 |

無鄰居時兩者退回預設規則，流程照常運作。已更新 [Y2_流程.md](../Y2_流程.md) 的 ② ③。

## Q17：所以 FORGE 三年都不適合參考？

**不是。Q7 只說 FORGE 不適合 Y2 ① 的架環境，沒有說三年都不適合。**

FORGE 資訊來源：arXiv 2606.03453 HTML 版，經擷取摘要閱讀，**未逐段讀全文**。

| | 適合程度 | 依據 |
|---|---|---|
| **Y1** | **最相關，可部分參考** | 論文：多個 agent 分工（情報、建環境、規劃、攻擊、偵測）做多輪攻擊；攻擊結果分 L0–L3 四級而非成功／失敗；等級由工具輸出判定而非 agent 自述（§3.2、§3.3）；攻擊時同步收集 trace |
| Y2 | 低 | 架環境方式不合（Q7）；可借的只有「建置→部署→測試＋防造假檢查」流程 |
| Y3 | 幾乎無 | FORGE 產出的是偵測規則（Sigma／Snort），不是程式修補 |

**Y1 參考時的限制**（論文內容＋我的推論，需祐廷判斷）：
- FORGE 從**已知 CVE** 出發做重現；Y1 若是要找未知漏洞，起點不同。（推論；Y1 範圍待確認）
- L0–L3 的定義以檔案讀取、資料外洩、RCE 為例（Table 1），**沒有針對越權類漏洞**；論文也沒有授權類 CWE 的結果，唯一一個授權繞過的 L3 案例還被列為可能誤判（§4.1）。
- 業務邏輯漏洞最難的是判斷「這算不算攻擊成功」（回應常是正常 200），FORGE 沒有處理這個問題。（推論）
- 測試網站沒有登入機制（§5.2），越權類漏洞需要多個使用者身分，無法直接沿用。
- 單一作者預印本、未經同儕審查；評分依賴 LLM。

**結論**：FORGE 主要是 Y1 的參考對象，是否採用由祐廷決定。Y2 只在環境建置流程上有小幅借鑑。

> **更正（見 Q18）**：「Y1 最相關」說過頭。FORGE 的前提是**已知 CVE**，這不是次要限制，而是整個流程的起點；Y1 若沒有已知漏洞描述，FORGE 的流程無法套用。

## Q18：FORGE 不是做最小可重現化嗎？Y1 沒有 PoC 如何重現？重現又能幹嘛？

**核對原文**（arXiv 2606.03453 HTML 版擷取，未逐段讀全文）：

1. **輸入不是 PoC，是已知 CVE**：§4.1「consumes only CVE metadata and the resolved package coordinates」；Intel agent 另會查 patch diff 與 ExploitDB（§3.1）。是否把既有 PoC 交給攻擊 agent，論文沒寫。
2. **只重現已公開漏洞**：§5.1「only publicly disclosed CVEs with assigned identifiers are processed」，不找未知漏洞。
3. **重現的用途是給防守方**：驗證漏洞優先序（EPSS／CVSS 與實際可利用性的關係）、產生偵測規則、檢查組織的偵測設施能否觀察到該攻擊（§1、§2.3、§5.3）。

**所以**：
- 問題不在「Y1 沒有 PoC」—— FORGE 本身也不需要 PoC，它需要的是**已知漏洞的描述（CVE）**。
- 關鍵是 Y1 的起點：
  - Y1 若是**面對一個網站、自己找出未知的邏輯漏洞** → 沒有 CVE 可餵，FORGE 流程無法套用。
  - Y1 若是**拿已知 CVE 產生攻擊**（例如做評測資料） → FORGE 才有參考價值。
  - Y1 是哪一種，要問祐廷（推論，筆記未明確記載）。
- FORGE 的目的（排優先序、寫偵測規則）三年都不是本計畫的目標。

**修正後的整體判斷**：FORGE 的問題設定（已知 CVE → 重現 → 防守用途）與三年都不吻合。可借的只剩通用做法：攻擊結果分級而非只有成功／失敗、由工具輸出而非 agent 自述判定結果、建置環境時的防造假檢查。這些做法不是 FORGE 獨有，引用價值有限。

> **更正（見 Q19）**：上文「FORGE 的目的三年都不是本計畫的目標」說得太粗。Y2 同樣是防守方，差別在防守的層次。

## Q19：Y2 不就是在做防守方嗎？

**是。** Q18 說「FORGE 的用途不是本計畫的目標」說得太粗，應該區分防守的層次：

| | FORGE | Y2 |
|---|---|---|
| 防守層次 | 營運層：哪個漏洞先修、怎麼在流量／日誌中偵測攻擊 | 程式碼層：程式錯在哪一行、為什麼錯 |
| 看不看程式碼 | 不看，把網站當黑箱 | 要看，沿呼叫鏈追 |
| 產出 | 偵測規則（Sigma／Snort）、可利用性分級 | 根因位置、被違反的規則、驗證過的探針 |
| 從攻擊 trace 產出的東西 | 比對攻擊特徵的規則 | 檢查不變量的斷言 |

**對 Y2 的可能用途（推論，未驗證）**：可作為**動機中的對照**。以 BOLA 為例，攻擊請求和正常請求長得一樣（`GET /orders/456` vs `GET /orders/123`），差別只在「這張訂單是不是你的」。從流量比對特徵的偵測規則很難區分兩者，必須回到程式碼層檢查擁有權 —— 這正是 Y2 要做的事。FORGE 原文沒有討論這點；它自報 93.4% 的 Snort 規則零誤報，但測試用的是合成的正常流量（依論文摘要與搜尋摘要，章節未核對）。

**不變的部分**：Q7（FORGE 的環境不適合 Y2 ①）與 Q18（FORGE 以已知 CVE 為起點）仍然成立。

## Q20：確定 Y2 不用給修復優先級？

**不確定，而且依現有文件，Y2 應該要給。** Q19 的表格暗示「排優先序是 FORGE 的事、不是 Y2 的事」，這是錯的。

**依據**：
- [Y2 README §2.6](../README.md)（筆記，來源未標明）：風險矩陣要「直接為 Y3 的 Multi-Hunk 修補提供修補位置與**優先順序**」。
- 計畫綱要 `003-三年計畫提出綱要-20261008.pdf`：投影片中文字型無法擷取，只讀得到英文片段（第 24 頁：Y2 輸入為「PoC + Attack Trace + Project Repo」），**無法確認綱要本身是否要求優先順序**。
- 設計文件 DR-00 把矩陣格子定義為「定位證據強度」，未納入修補優先順序 —— 與 README 不一致。

**「優先級」要分三種**（我的整理）：

| 種類 | 問題 | 歸屬 |
|---|---|---|
| 定位排序 | 哪個候選位置最可能是根因 | Y2（設計文件已有） |
| **修補優先順序** | ③ 找到的多個受影響入口，先修哪個 | **Y2，依 README 應提供，流程目前缺** |
| 組織層級漏洞排序 | 全公司這麼多漏洞，先處理哪個 | 營運層（FORGE、CVSS／EPSS），非 Y2 |

**修補優先順序可用的依據**（推論，皆為 Y2 手上已有的資訊）：
- 是否為 Y1 實際打穿的入口（vs 推論有同樣的洞）。〔更正：原寫「是否經 ④ 驗證」，但 ③ 在 ④ 之前，排序時還沒有驗證結果〕
- 操作種類（讀取 vs 修改 vs 刪除）
- 誰能觸及（未登入 vs 一般使用者）
- 資料敏感度（依資料表結構）

**待定**：Y3 實際怎麼使用優先順序（多處修補可能一次全修），需與羿君確認。

**附帶發現（與 Q18 相關）**：投影片第 24 頁英文片段顯示 Y1 的輸入是「App / Server」、輸出是「PoC + Attack Trace」；[三年度計畫整合與架構設計.md:194](../../三年度計畫整合與架構設計.md)（與 Gemini 的對話紀錄）也記載祐廷的 Agent「找漏洞＋發動攻擊＋驗證 BOLA」。兩者都指向 Y1 是**面對網站找漏洞**，不是從已知 CVE 出發，FORGE 與 Y1 更不吻合。仍待祐廷確認。

## Q21：FORGE 的優先級和 Y2 的優先級差在哪？

已在 [Y2_流程.md](../Y2_流程.md) ③ 加入 3-4「排出修補優先順序」。

**差在排序的對象不同**：

| | FORGE | Y2 |
|---|---|---|
| 排什麼 | **很多個不同的漏洞**（603 個 CVE，分屬不同軟體） | **同一個漏洞出現的多個位置**（同一個專案、同一條被違反的規則） |
| 回答的問題 | 這些漏洞哪些真的打得進去、能打多深？先處理哪一個？ | 這個洞出現在 3 個入口，先補哪一個？ |
| 時間點 | 決定要不要處理之前 | 已經確定要修之後 |
| 給誰 | 資安團隊（排工作順序） | Y3／工程師（排修補順序） |
| 依據 | 實際攻擊能達到的等級 L0–L3，與 CVSS／EPSS 比較 | 是否被 Y1 實際打穿、操作種類、誰能觸及、資料敏感度 |

**例子**：

```
FORGE 排的：
  CVE-A（某套件路徑穿越）→ L2，可讀任意檔案
  CVE-B（某套件 SSRF）   → L0，打不進去
  → 先處理 CVE-A

Y2 排的（同一個「缺少訂單擁有者檢查」）：
  1. DELETE /orders/{id}         刪除，一般使用者可觸及
  2. GET    /orders/{id}         讀取，Y1 實際打穿
  3. GET    /orders/{id}/export  讀取，推論有同樣的洞
  → 先補 1
```

FORGE 的排序**跨漏洞**，Y2 的排序在**一個漏洞內部**。兩者不衝突：FORGE 這類工具決定「先處理哪個漏洞」，Y2 決定「這個漏洞的多個位置先補哪裡」。

**附帶更正**：Q20 列的依據「是否經 ④ 驗證」有誤 —— ③ 在 ④ 之前，排序時還沒有驗證結果，已改為「是否為 Y1 實際打穿的入口」。

## Q22：Y2 的驗證是跑整個程式，而非 FORGE 那樣的最小驗證？為何不能最小驗證？

**是，要跑整個原專案。** 原因：

1. **漏洞位置不同**：FORGE 的漏洞在套件內部，套件本身完整，隨便寫個小網站呼叫就會出現。Y2 的漏洞在網站自己的程式，存在於 Controller、Service、資料庫之間的關係。
2. **縮小需先知道根因 → 循環**：要知道哪些程式可刪，就得先知道哪些與漏洞有關，而這正是 Y2 要回答的；刪錯就可能把根因刪掉。
3. **③④ 需要的東西小網站沒有**：其他網址（找同樣的洞、數團隊習慣）、真實的正常操作（④ 確認不誤傷）、登入機制與多使用者資料（越權需要「別人的資料」；FORGE 自承無登入，§5.2）。
4. **評估要比對真實修補**，只能在原專案做。

**代價**：環境較重（資料庫、相依套件）。解法：沿用 Y1 的環境（已列待辦）。

**可縮小的是攻擊請求，不是程式**（推論，未驗證）：如 Y1 用 10 個請求，找出只需其中 3 個即可觸發，讓 ① 記錄的路徑更乾淨。對應 Zeller 的 delta debugging（設計文件 [^14]）。

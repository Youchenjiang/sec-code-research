# 函式路徑風險矩陣：軸向與特徵設計決策

## 0. 這份文件要定下什麼、不定什麼

**要定下的**：矩陣的列（函式路徑）與欄（違反的不變式）各自的形式定義、粒度選擇、以及每個 cell 要填入哪些可計算的證據特徵。每個決策都附替代方案、取捨、以及「在什麼證據出現時應該推翻這個決策」。

**不在本文**：證據如何聚合成分數、權重怎麼來、校準方法、ground truth 建構、Top-k/MRR 等評估指標、assertion probe 的實作細節。這些依賴本文定下的軸向，之後另立文件。

**先決前提**（Year-2 的輸入契約）：黑箱 exploit 與其執行 trace 已存在。也就是「這個端點確實有業務邏輯漏洞」是**已知前提**，不是待證結論。

---

## 1. 最根本的一個定位決策

### DR-00：矩陣是 localization 的工具，不是 detection 的工具

**決策**：cell(p, i) 的語意固定為——

> 「**在已知該 exploit 成立的條件下**，路徑 p 是不變式 i 被違反的**責任位置**，其相對證據強度。」

而不是「路徑 p 存在漏洞 i 的機率」。

**為什麼這個區分是整篇方法的地基**：

1. **它改變了特徵的篩選標準。** detection 工具必須在全庫掃描下壓低誤報，因此傾向只採用高精確度、低召回的保守證據。localization 條件於「漏洞確實存在」且候選集合已被 trace 限縮到單一端點，所以可以放心採用高召回、低精確度的證據——它們在候選集合內部仍有排序能力，在全庫掃描下卻會淹沒使用者。〔待補：以 BolaRay[^3] 等 detection 工具實際報告的誤報率佐證此段；本次未取得全文，引用前需自行核對原文數據。〕
2. **它改變了與既有工作的關係。** Waler[^4]、BolaRay[^3]、Anota[^5]，以及針對 Web 存取控制的 MACE[^10]、Sun et al.[^12]，都在回答「哪裡有漏洞」；predicate switching[^2]、SBFL[^8][^9]、delta debugging[^14] 都在回答「已知失敗，哪裡該負責」，但針對的是會當掉或斷言失敗的 crash-like 故障。本工作要填的空格是：**把 fault localization 的條件式提問，搬到「沒有 oracle、故障表現為一次完全合法的 HTTP 200」的業務邏輯場景**。這句話就是 proposal 的卡位句。
3. **它定義了「正確答案」。** ground truth 不是「這段程式有漏洞」，而是「修補 commit 動到的位置」。這讓評估可以錨定在真實修補紀錄上。

**推翻條件**：若實驗顯示在候選集合內排序，與全庫掃描的排序沒有顯著差異（亦即 trace 條件化沒帶來資訊），則本定位失效，應退回 detection 框架。

## 2. 列（Row）：函式路徑的粒度

### DR-01：列的單位是「入口到 sink 的過程間呼叫路徑」，不是函式、不是類別

| 選項 | 取捨 |
|---|---|
| 單一函式 | 最便宜、對齊 SBFL 習慣。但在 Spring 裡 **guard 與 sink 幾乎永遠不在同一個函式**（guard 在 controller 或切面，sink 在 service/repository），以函式為單位會讓「缺漏的關係」無處表達 |
| 呼叫邊 (caller→callee) | 能表達關係，但一條授權鏈常跨 3–5 層，兩兩邊無法表達「整條鏈上都沒有人檢查」 |
| **呼叫路徑（call-string）** | **採用**。唯一能承載「整條鏈缺席」這個語意的單位 |
| ICFG 完整路徑（含分支序列） | 表達力最強，但數量爆炸且對讀者不可讀 |

**決策**：列 = 從 Spring handler 方法到 security-sensitive sink 的**有序方法序列** `p = ⟨m₀, m₁, …, mₖ⟩`，其中 `m₀` 是 handler，`mₖ` 是 sink。分支條件不進入列的身分，而是以特徵形式進入 cell。

**代價**：同一組方法但走不同分支的兩次執行會被折疊成同一列。這在 guard 位於分支內時會損失資訊。**緩解**：以 DR-04 的「守衛指紋」把關鍵分支結果掛回 cell，而不是拆列。

---

### DR-02：sink 的定義採「狀態可觀測效果」，不採「敏感 API 清單」

**決策**：sink = 下列任一：
- 對受保護實體的持久層讀/寫/刪（JPA repository 方法、`EntityManager` 呼叫、`@Query`、原生 SQL 執行點）
- 進入 HTTP 回應體的實體序列化點（`@ResponseBody` 回傳、`ResponseEntity.body`）
- 外部副作用（寄送、付款、檔案輸出、訊息發佈）

**理由**：業務邏輯漏洞的危害定義在「哪個物件被誰動到」，不在「呼叫了哪個危險函式」。資料層 sink 還有個工程上的好處——它是**可機讀的歸屬錨點**：SQL 的 `WHERE` 子句直接告訴你這次操作的物件由哪些述詞界定。BolaRay 的核心洞見正是用 SQL 層反推物件層授權模型[^3]，這點值得直接繼承。

**代價**：讀取類 sink 數量龐大（每個查詢都是）。**緩解**：只有被 exploit trace 觸及、或與 trace 觸及實體同型的 sink 進入候選。

---

### DR-03：列的列舉以 exploit trace 為骨幹，但**必須包含反事實路徑**

這是列設計裡最容易被做錯的一步。

**問題**：根因是一個**缺席**——少了一個擁有權檢查、少了一個狀態前置條件。缺席的東西按定義不會出現在 trace 裡。純粹從 trace 取列，等於只列出「做了什麼」，而漏洞在於「沒做什麼」。

**決策**：列集合 = `R_exec ∪ R_cf`
- `R_exec`：exploit trace 實際執行的入口-sink 路徑（靜態解析虛擬呼叫的歧義由 trace 消解，這是有 trace 的最大紅利）
- `R_cf`（反事實路徑）：**在同儕端點上存在、但在本端點上不存在**的檢查位置所構成的路徑。來源有三：
  - 同一 controller 的其他 handler 走向同型實體 sink 的路徑
  - 同一 repository 方法在其他呼叫點的前置守衛位置（即 MACE 的授權上下文一致性：比對到達同一資源的各入口是否施加相同授權條件[^10]）
  - 版本歷史中曾經存在、後被移除或未被複製的守衛位置

每條 `R_cf` 的列額外帶一個 `absent: true` 標記與其同儕來源，使「這條路徑該有但沒有」成為可排序的對象。

**替代方案**：只用 `R_exec`，把缺席表達成「路徑上守衛數為 0」這個特徵。**否決理由**：那只能說「這裡沒檢查」，無法說「這裡**本來該**檢查」，而後者才是根因報告對工程師有用的形式，也才能直接推導出 assertion probe 要插在哪一行。

**成本與風險**：`R_cf` 的列舉需要「同儕」的定義（DR-05），而同儕定義錯誤會灌入大量雜訊列。這是本設計目前最大的工程風險。

---

### DR-04：路徑爆炸以三道閘門控制，不以單一 k-limiting

| 閘門 | 作用 | 來源 |
|---|---|---|
| trace 消解 | 虛擬呼叫、Spring 代理、反射注入的目標由 trace 固定，消除最大宗的靜態歧義 | 動態 |
| thin slicing | 只保留對 sink 的物件識別與授權判定有 **producer** 關係的語句，丟棄控制流與容器操作的雜訊 | [^6] |
| 同構折疊 | 僅差在委派方法、getter、`Optional` 包裝的路徑折疊為一列，保留代表元與折疊計數 | — |

**理由**：`k`-limiting 是語法閘門，會均勻地砍掉長路徑，但業務邏輯的授權鏈本來就長。thin slicing 是語意閘門，砍掉的是與「誰能動這個物件」無關的部分——方向正確得多。

---

### DR-05：同儕關係（peer）的定義分三層，並顯式記錄所用層級

`R_cf` 與後面 E 類特徵都依賴「同儕」。模糊的同儕定義會讓整個差分訊號失真。

1. **L1 實體同儕**：操作同一 JPA 實體型別的 handler（最嚴格，訊號最乾淨）
2. **L2 類別同儕**：同一 `@RestController` / `@Service` 內的其他公開方法（反映團隊在該檔案的局部慣例）
3. **L3 慣例同儕**：全專案中具有相同 HTTP 動詞 + 路徑參數形狀（如 `/{id}`）的 handler（覆蓋面最大，雜訊也最大）

**決策**：三層都算，但每個差分特徵**必須攜帶其同儕層級**，不得混合平均。理由：L1 的「同儕有我沒有」幾乎必然是缺陷，L3 的同樣結論常常只是設計差異（公開端點本來就不需要擁有權檢查）。把它們平均掉，等於把最強的訊號稀釋進最弱的訊號裡。

## 3. 欄（Column）：違反不變式的分類法

### DR-06：分類軸以「程式碼證據可區分」為準，**不以 CWE 為準**

**否決 CWE 作為欄位**。CWE-639（Authorization Bypass Through User-Controlled Key）、CWE-285（Improper Authorization）、CWE-862（Missing Authorization）在原始碼層面的證據形狀幾乎相同——都是「principal 未參與 sink 的約束」。用 CWE 當欄，會讓同一份證據同時點亮三欄，矩陣失去判別意義。CWE 應該在報告階段從本分類法映射過去，而不是反過來。

**採用原則**：兩個欄位能並存，**若且唯若**存在至少一個特徵能把它們分開，而且存在不同形狀的 assertion probe 能分別證偽它們。

### 候選欄位（v1 七欄）

| ID | 不變式 | 違反的形式述詞（非形式陳述） | Java/Spring 可觀測代理 | probe 形狀 |
|---|---|---|---|---|
| **I1** | 物件歸屬 | 存在 sink 操作物件 o，使得 `owner(o) ≠ principal` 且無述詞約束兩者 | sink 查詢的 `WHERE` 不含可連結 principal 的欄位；請求參數直接成為主鍵 | 在 sink 前斷言 `owner(o) == principal` |
| **I2** | 功能/角色層級授權 | principal 的角色集不含執行該 handler 所需角色 | 無 `@PreAuthorize`/`@Secured`；`SecurityFilterChain` 僅 `authenticated()` | 斷言 `hasRole(required)` |
| **I3** | 工作流順序 | 物件狀態 s 不在允許的前置狀態集內即發生轉移 | 狀態欄位的「讀-比較-寫」模式缺少比較環節 | 斷言 `s ∈ allowedPrev(transition)` |
| **I4** | 一次性／冪等 | 同一邏輯操作被套用 n>1 次仍生效 | 缺少唯一性約束、樂觀鎖版本欄、冪等鍵 | 斷言「該操作在本物件上的累計次數 ≤ 1」 |
| **I5** | 數值完整性 | 關鍵數值（金額、數量、折扣）來自請求而非伺服器端重算 | 請求 DTO 欄位直接流入持久化數值欄 | 斷言 `persisted == recompute(server-side)` |
| **I6** | 租戶／範圍隔離 | 跨租戶邊界的物件進入結果集 | 缺少 tenant 判別欄或 Hibernate filter 未啟用 | 斷言 `tenant(o) == tenant(principal)` |
| **I7** | 條件適用性 | 適用前提（有效期、資格、額度）未被驗證 | 規則欄位被讀出但未進入任何分支條件 | 斷言該前提謂詞為真 |

### DR-07：欄位非互斥，cell 採 multi-label

一次 BOLA 常同時是 I1 與 I6（租戶隔離是歸屬的一種特例）。強制互斥會逼出任意的切分規則。**決策**：允許一條路徑在多欄同時有高證據，並在報告層加一條「主導欄位」的呈現規則（另文）。

### DR-08：每欄必須同時提供三件事，缺一不得進入 v1

1. **形式述詞**：違反時為真的邏輯式
2. **可觀測代理**：該述詞在 Java/Spring 中可由靜態或動態分析取得的替身，連同其已知不完備性
3. **probe 模板**：能把「代理成立」升級為「述詞成立」的斷言形狀

**理由**：這條規則是防止分類法膨脹成一張沒人能實作的名詞表。它也直接接上 Anota 的作法——以人工標註把應用語意編碼成可被監控的政策[^5]；差別在於 Anota 用標註**驅動 fuzzing 找漏洞**，本工作用 probe **確認一個已排序的根因假設**，標註量因此被壓到 Top-k 條路徑而非全應用。

### DR-09：不設第三軸；證據來源與信心壓進 cell

考慮過加第三軸「證據來源（靜態／動態／差分）」。**否決**：三維矩陣既不可讀也不可排序，而且來源本來就是 cell 內特徵向量的分組標籤，沒有獨立的軸地位。

### DR-10：cell 的內容不是一個純量

**決策**：`cell(p, i) = { evidence: [特徵值向量], provenance: [來源與層級], probe: 模板實例, refutation: 反駁條件 }`。分數是這個結構的衍生物，不取代它。

**理由**：純量分數無法回答工程師的下一個問題——「憑什麼」。`refutation` 欄位尤其重要：它明確寫出「若觀察到 X，本 cell 應降為零」，讓矩陣可被證偽，而非只能被相信。

## 4. 特徵集

每個特徵記錄：定義、來源、判別方向、已知失效模式。失效模式必須寫，因為它是後續誤報分析的唯一線索。

### A 類：靜態結構

| ID | 定義 | 判別方向 | 已知失效模式 |
|---|---|---|---|
| A1 | sink 可達性與路徑長度 | — | 框架反射呼叫使靜態圖不完整 |
| A2 | **principal-to-sink 約束距離**：principal 物件經資料流是否成為 sink 查詢述詞的一部分 | 無連結 → I1/I6 強證據 | principal 經 ThreadLocal/AOP 間接注入，資料流追不到 |
| A3 | **外部參數到物件識別碼的污染**：請求參數是否直接成為實體主鍵 | 直達 → I1 強證據 | 參數先經雜湊/UUID 轉換仍可能是 IDOR |
| A4 | **無守衛後綴長度**：最後一個守衛到 sink 之間的語句數與分支數 | 越長 → 各欄皆升 | 守衛辨識錯誤時全盤失真（見 DR-11） |
| A5 | **支配缺席**：同儕路徑上支配 sink 的守衛，在本路徑上不支配 | 是 → I1/I2/I3 強證據 | 依賴同儕定義（DR-05） |

### B 類：框架與註解（Spring 專屬，成本最低、判別力最高）

| ID | 定義 | 判別方向 | 已知失效模式 |
|---|---|---|---|
| B1 | 方法/類別上 `@PreAuthorize`/`@PostAuthorize`/`@Secured`/`@RolesAllowed` 的存在與**述詞形狀**（是否引用 `#id`、`principal`、`returnObject`） | 只有角色判定、不引用物件 → I2 已守但 I1 未守 | 註解在介面上而實作被代理繞過 |
| B2 | `SecurityFilterChain` 中對應該 URL 的規則強度 | 僅 `authenticated()` → I1/I6 升 | 路徑樣式比對歧義 |
| B3 | AOP 切面／`HandlerInterceptor` 覆蓋該路徑與否 | 未覆蓋 → 全欄升 | 條件化切面（`@Conditional`）靜態不可判 |
| B4 | **守衛有效性旗標**：註解存在但因 Spring 代理語意失效（self-invocation、`private`/`final` 方法、非 Bean 呼叫） | 存在但失效 → **比完全沒有更強的證據** | 需要精確的代理模型 |

B4 值得單獨說明：它捕捉的是「開發者以為有檢查、實際上沒有」的情形。這類根因在人工 review 中最難發現（因為眼睛看到註解就放心了），卻恰好是自動化最擅長的。把它當成高權重特徵而非噪音，是本設計刻意的選擇。

### C 類：資料層（繼承 BolaRay 的錨點思路[^3]）

| ID | 定義 | 判別方向 |
|---|---|---|
| C1 | sink 查詢述詞集合是否含 owner/tenant 欄 | 不含 → I1/I6 |
| C2 | 受影響實體的**歸屬模型推論**：公開 / 直接擁有 / 經父物件間接擁有 / 角色管控 | 推論為「直接擁有」但 C1 為否 → I1 最強證據 |
| C3 | 間接歸屬的 traversal 深度（如 comment → post → author） | 深度 ≥ 2 且無 join 約束 → I1 |
| C4 | 寫入語句的影響範圍是否完全由外部參數決定 | 是 → I1/I5 |

### D 類：動態 trace

| ID | 定義 | 判別方向 | 備註 |
|---|---|---|---|
| D1 | 路徑是否在 exploit trace 中執行 | 執行 → 進入 `R_exec` | — |
| D2 | **exploit 與 benign 的分支向量差集** | 差異分支即候選責任點 | 需要 benign trace；見 §6 未決問題 |
| D3 | **身分無感守衛**：同一守衛在攻擊者身分與合法身分下判定值相同 | 相同 → 該守衛與身分無關，I1/I2 升 | 本設計中判別力最高的動態特徵 |
| D4 | 頻譜式可疑度（Ochiai 等[^9]） | 依公式 | 需多組 pass/fail 執行，Year-2 是否投入待定 |

D3 是把 predicate switching 的精神[^2]搬進授權場景的具體作法：不翻轉述詞的真值，而是**替換述詞的身分輸入**，觀察判定是否改變。若不改變，該述詞就不可能是授權守衛，整條路徑的「有守衛」假象隨之瓦解。

### E 類：同儕差分

| ID | 定義 | 同儕層級 |
|---|---|---|
| E1 | 同儕 handler 的守衛集合與本路徑的**差集** | L1/L2/L3 分別計算 |
| E2 | 同一 repository 方法在其他呼叫點的前置守衛，本呼叫點是否缺 | L1 |
| E3 | 版本歷史：該守衛是否曾存在後被移除，或新端點複製自舊端點而漏抄 | — |

E 類整體承襲「從重複樣本中找偏離行為」的思路[^13]、MACE 跨入口比對授權上下文一致性的作法[^10]，以及 Waler 以動態觀察推論行為規格、再找違反路徑的兩段式結構[^4]；差別在於本工作不需要規格具備全域正確性，只需要在同儕集合內具備相對性。

### F 類：守衛辨識（前置子問題）

### DR-11：「什麼算一個授權守衛」採三來源混合，並記錄來源

A4、A5、D3、E1 全部依賴「守衛」這個概念。守衛辨識錯了，上面一半的特徵一起失真——這是整個特徵集的**單點故障**。

**決策**：
1. **框架白名單**（最可靠）：Spring Security API、方法註解、`AccessDecisionManager`/`AuthorizationManager` 實作
2. **挖掘式**（覆蓋自訂守衛）：以 ACMiner 的作法為範本——從大量入口點的共同前置條件中統計地抽出授權檢查[^1]。ACMiner 原本針對 Android middleware，但「入口點集合 + 共同前置條件挖掘」的結構對 Spring controller 集合同樣成立
3. **人工標註**（fallback）：Anota 式的輕量標註[^5]，僅用於前兩者皆未命中、且落在 Top-k 的路徑

每個被辨識的守衛攜帶來源標籤，使後續誤報分析能回答「是分類錯了，還是守衛辨識錯了」。

## 5. 否決清單（被認真考慮過但不採用）

| 方案 | 否決理由 |
|---|---|
| 以 CWE 當欄位 | 證據形狀無法區分（DR-06） |
| 以檔案或類別當列 | guard 與 sink 跨類別，無法表達缺席關係（DR-01） |
| 第三軸「證據來源」 | 不可讀、不可排序，且本就是 cell 內分組（DR-09） |
| 單一純量 risk score 作為 cell | 無法回答「憑什麼」，不可證偽（DR-10） |
| 讓 LLM 直接對路徑打分作為 v1 主幹 | 對審稿人不可驗證、不可重現。**保留**用途：守衛命名語意判讀、實體歸屬模型的初始猜測、平手時的排序，皆須人工可覆核 |
| 只用 exploit trace 取列 | 缺席的守衛不在 trace 裡（DR-03） |
| 把同儕層級平均成單一差分分數 | 最強訊號被最弱訊號稀釋（DR-05） |

## 6. 未決問題（下一份文件要解的）

1. **路徑等價類**：折疊規則（DR-04）目前只排除委派與 getter。深層委派鏈（Spring Data 動態代理產生的 repository 實作）是否該整段視為單一邊？
2. **反事實列的上限**：`R_cf` 沒有自然邊界。需要一個基於同儕層級的配額規則，否則 L3 同儕會灌爆列數。
3. **沒有 benign trace 時的退化路徑**：D2、D3 都需要第二組身分的執行。若 Year-2 的輸入只保證一條 exploit trace，必須設計「以同一端點的合法請求自行重放產生 benign trace」的程序，並評估這對目標系統的侵入性。
4. **歸屬模型不明確時的 C2**：當實體沒有明確 owner 欄位（歸屬藏在中介表或應用層快取），C2 無法推論。是否退回 I6 或標記為不可判定？
5. **守衛「存在但恆真」**：B4 處理代理失效，但未處理條件恆真（如 `if (user != null)`）。D3 部分覆蓋，是否需要獨立的靜態恆真偵測？
6. **跨欄證據共享的記帳**：C1 同時支持 I1 與 I6。在不設聚合模型的前提下先不處理，但分數設計時必須避免重複計入。
